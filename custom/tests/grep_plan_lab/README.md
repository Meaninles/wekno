# grep_chunks 本地验证与完整方案评估（2026-09-12）

本文保留前一轮实验记录。后续本地正式实现和验收见
[GrepChunks 同步检索投影](../../../docs/custom/GrepChunks同步检索投影.md)，实验脚本仍不等于正式迁移。

## 结论与边界

推荐进入应用集成验证的方案是：**同一 PostgreSQL 内的紧凑有效切片检索投影 + 完整权限范围条件 + 原正文/标题正则 + 唯一排序 + 选中后回源 + 同事务维护**。

它不按问题类型分流，不替换为 BM25，不降低候选上限。不是只改 `force_custom_plan`。

这是经过本地数据面/SQL/维护原型验证的架构候选，**不是已完成生产验收的实现**。没有修改应用代码、生产数据、生产配置。没有复现生产 49 秒的物理磁盘长尾，不能宣称生产一定降至这里的毫秒数。

## 实验环境

- 使用现有 `WeKnora-postgres-dev`，没有保留额外数据库服务。
- 所有实验表、索引、函数和触发器位于 `grep_plan_lab_20260912`。
- 应用 `public` 表只读，没有变更应用表索引、触发器、配置。
- 从本地真实切片复制前 300,000 条及标题，重新分配为 20 个知识库/4 个租户，并制造禁用、删除状态；正文保持本地内容。
- 固定七库范围有 45,530 条有效切片，与先前生产约 43,532 条的数量级接近，但不是生产数据副本。
- 全部有效投影 125,747 条；堆约 73.5 MiB，初始含索引约 93.3 MiB。后续维护测试补充 knowledge_id 索引。
- 本机 PostgreSQL shared_buffers 128 MiB，Docker 总资源及磁盘不同于生产。未清空操作系统缓存、未限制物理盘速率。
- 基线增加了 `created_at DESC, id DESC` 唯一排序，用于可重复比较；不是历史生产 SQL 的逐字重放。
- 初阶段比较 ID/时间戳；payload.py 另测正文、标题、文档 ID、知识库 ID、类型、时间戳和文档切片数量。没有覆盖全部生产 metadata/source_locator 字段。

## 实际比较与排除

1. 原查询 + 通用/专用计划：本地并未出现生产同等程度的计划退化。
2. 强制物化授权范围：多数样本更慢，排除。
3. 单独增加有效切片范围索引：有局部收益，不构成完整解法。
4. 增加正文/标题 trigram：保留跨表 OR 时，多数样本仍扫描大量切片页。
5. 正文/标题分别查再 UNION：零结果可非常快，但宽泛词退化。
6. ILIKE 必要字面量预筛选 + 原正则：长词可能受益，但短词/复杂正则出现重复工作，不推荐当前原型。
7. 按知识库 LATERAL + 上述预筛选：宽泛词出现约 1.6 秒、并发最高约 2 秒退化，排除。
8. 紧凑有效切片投影：10 类测试均比归一化基线快，选为推荐方向。
9. 投影再按库 LATERAL：全匹配更快，但向量并发时尾部不如直接投影稳定，暂不作为默认方案。

对中文正则的实验发现仅限于当前环境和查询：部分 `~` / `~*` 查询未选择 trigram，而对应 `ILIKE` 查询可选择。不能泛化为“PostgreSQL 不支持中文正则索引”。

## 延迟结果

projection_results.json：每类单线程 SQL 各执行 3 次，下表中位数，单位 ms。

| 查询 | 归一化基线 | 直接投影 |
|---|---:|---:|
| 合同金额组合 | 201 | 124 |
| 预案 | 163 | 96 |
| 单库宽泛词 | 110 | 52 |
| 多库宽泛词 | 160 | 84 |
| 信息化基础设施 | 175 | 111 |
| 无匹配 | 200 | 130 |
| 复杂正则 | 187 | 121 |
| 单字 | 154 | 90 |
| 全匹配 | 97 | 35 |
| 可选表达式 | 98 | 39 |

4 并发、每方案 40 次混合查询：

| 场景 | 基线样本 P95 | 投影样本 P95 | 基线最大 | 投影最大 |
|---|---:|---:|---:|---:|
| 仅 grep | 203 | 134 | 255 | 137 |
| grep + 2 个向量扫描 | 229 | 139 | 240 | 144 |

向量负载来自本地真实 10,000 条向量，约 77 MiB；查询为顺序距离扫描并取 200 条。不是生产 ANN 执行计划重放。40 个混合样本的 P95 只是本次样本统计，不能用作生产 SLA。

基线常访问约 22,844 个 shared blocks，投影约 4,501 个。投影首轮约读取 3,678 页，后续可全部命中 PG 缓存；基线多次仍读取约 22,000 页。PG read 不等于物理磁盘读取，操作系统可能命中缓存。

payload_results.json：加上正文回源与原口径切片计数后，各样本仍更快。计数约 0.4–2 ms，不是这批样本瓶颈。**计数不能直接改为投影行数**，因为原计数包含 summary，而 grep 候选排除 summary。

## 效果与权限验证

- 10 类输入：合同组合、短词、单库宽泛词、多库宽泛词、长词、零结果、复杂正则、单字、`.*`、可选表达式。
- 对比有序候选 ID；并发及向量干扰下保持一致。
- 正文独占命中、标题独占命中、两者同时命中，各有 600 条相同时间戳的边界数据，前 500 条完全相同。
- 禁用、summary、软删除、错误租户、未发布文档的定向探针不得返回。
- @文件、@标签、@知识库与上述混合范围，样本有序候选一致。这里标签是实验关系表，不是调用前端授权流程。
- 正文/标题/部分来源字段和文档切片计数对比一致。
- 原生 grep 排序、覆盖、引用相关已有单元测试在现有 Linux API 容器运行通过：

```text
go test ./internal/agent/tools -run 'Test(Grep|CompileGrep|SelectGrep|BuildGrep)' -count=1
ok github.com/Tencent/WeKnora/internal/agent/tools 0.458s
```

Windows 原生执行被 DuckDB 的平台构建约束阻断，不是这些测试断言失败。

原查询同时间戳内顺序不确定，原去重/MMR 在同分时又可能依赖输入顺序。因此增加唯一排序是有意的稳定性修正，不承诺和某次历史不确定结果逐条一致。没有完整运行新路径的最终 MMR/聚合/LLM 对话，也没有标注答案质量评测。

## 推荐完整实现结构

### 查询：始终同一条流程

1. 沿用现有授权解析，得到 KB-tenant 对、文件 ID、标签范围；不新增问题分类器。
2. 在有效切片投影执行原 `content ~* pattern OR title ~* pattern`，全部权限条件保持；标签仍按关系表约束。
3. 按 `created_at DESC, id DESC` 取全局 500 条，而不是每库给前端 500 条。
4. 按这些 ID 回源拿完整 chunk、metadata、source_locator 等；整个读取在一致快照内完成。
5. 保留原计数、去重、打分、覆盖、MMR、最终输出上限和引用逻辑。

投影保存：chunk_id、knowledge_id、knowledge_base_id、tenant_id、created_at、content、knowledge_title。物理顺序/聚簇按租户和知识库组织；为范围、排序、文档回填建立 B-tree。数据增长后仍需监测表膨胀，初建时的紧凑布局不保证长期自动维持。

`scope_modes_results.json` 显示：直接投影在 custom/generic/auto 三种模式中候选一致；auto 确实经历 5 次 custom + 5 次 generic，但本次未产生长尾。因此最终方案不能依赖“永久强制 custom”这一个开关。是否保留局部 custom，需要应用集成后继续对照，不全局修改。

### 写入：同事务一致性，不用异步缓存

投影必须和源数据同事务更新，不允许异步索引落后导致漏检或暴露已撤回文档。需要覆盖切片创建、替换、正文变更、有效状态、类型、删除恢复，以及文档标题、发布、删除状态。

本地触发器原型验证了：插入、撤回、提交前后另一连接可见性、重新发布、改标题、禁用/启用、软删除/恢复、summary/正文切换、改正文、物理删除、事务回滚。

实际代价：31,583 条有效切片的大文档改标题，连同投影维护约 **489 ms**，回滚后原数据恢复。不能说读加速没有写成本。

生产实现应采用批量/statement-level 更新，统一多文档锁顺序，验证跨文档移动、并发更新、删除竞态和死锁重试。实验原型的逐行触发器和 advisory lock 只用于验证基础生命周期，**不能直接作为生产迁移使用**。

### 建设与上线

- 二开模块放 `internal/custom/modules/`，迁移放 `migrations/custom/`，原生 grep 只保留必要调用点。
- 初次回填必须有一致性水位/写入保护，完成源表与投影集合校验再切读，禁止未完成回填时读不完整投影。
- 同步查询必须保证投影与回源的一致快照；权限仍在查询层检查。
- 埋点分别记录连接等待、SQL、回源、计数、去重、MMR；超时明确失败，不把超时当“无结果”。
- 不在本次证据不足时拍定生产超时、全局并发数或继续加内存。先测生产等规模并发 P95/P99、向量共载和冷缓存。
- 上线前补齐混合授权真实入口、完整 payload/最终引用回归、大批导入/重切片、写入吞吐、竞争更新和恢复测试。

## 可复现文件

- lab.py / results.json：基础方案及索引分阶段比较。
- extended.py / extended_results.json：预筛选、UNION、LATERAL 反例。
- projection.py / projection_results.json：紧凑投影与并发。
- acceptance.py / acceptance_results.json：边界及向量共载。
- payload.py / payload_results.json：回源和计数。
- lifecycle.sql、lifecycle.py / lifecycle_results.json：同步维护原型。
- scope_modes.py / scope_modes_results.json：文件/标签/混合范围与计划切换。

运行顺序是上述文件顺序，lifecycle.sql 在 lifecycle.py 前。脚本会创建固定实验对象，默认不覆盖已有实验数据；不要在已存在最终索引/触发器的 schema 中重跑基线。重新实验应显式换一个新 schema，并由人确认实验对象清理范围。

本轮在已有 PG 容器内用 Python + psycopg 的纯 Python 实现运行，绕过 Windows 到 Docker 的 PG 端口连接问题；没有新起常驻服务。脚本可由 `docker cp` 放入 `/tmp/grep_plan_lab/`，通过 `GREP_LAB_IN_CONTAINER=1` 使用容器本地 socket。依赖位于实验临时目录，不修改应用镜像。
