# Qwen 关闭思考后的结束标记与重复回答分析

日期：2026-09-06。范围：当前 Qwen3.8-27B-Agent 的非思考工具调用链路。本轮仅分析、诊断请求和证据归档，未修改应用代码、网关运行配置、生产 WeKnora 或模型服务。部署输出预算仍为 8192；小型诊断请求使用 512，异常回答以 stop 正常结束，没有耗尽预算。

## 结论

关闭思考参数确实到达上游，但当前模型服务仍可能生成“回答 + `</think>` + 再次回答”。已在一个工具回传样例中，通过控制变量定位到模型可见工具定义中的 `strict:false` 是触发因素；SGLang 会自动补入这个字段。随后，非思考状态的解析器将没有起始标签的结束标签当作正文透传。

这构成已验证的链路：工具定义默认字段进入模板 → 当前模型生成异常格式 → 解析器按普通正文返回。不能将一个样例的实验推广成所有 Qwen 异常的唯一原因，也不能据此解释模型内部为何对这个字段敏感。

## 运行状态及实际请求

上游 `/get_server_info` 返回版本 `0.5.10+7a7f3c06`，模型与 tokenizer 路径均为 `<MODEL_PATH>`，reasoning parser 为 `qwen3`，tool parser 为 `qwen3_coder`，未设置显式 chat_template 覆盖。

在网关 Pod 内的独立诊断进程中截取 Router 实际发送的 HTTP 请求：

```json
{
  "chat_template_kwargs": {
    "enable_thinking": false,
    "preserve_thinking": true
  },
  "temperature": 0.7,
  "top_p": 0.8,
  "top_k": 20,
  "min_p": 0.0,
  "presence_penalty": 1.5,
  "repetition_penalty": 1.0
}
```

请求不包含 reasoning_effort。第一步 lookup_record 工具调用正常，提供合成记录 R17 的状态后，第二步返回重复回答。上游 logprobs 中逐 token 包含两段回答及 `</think>`，说明它们来自生成输出。绕过网关直接请求上游也能复现。

证据：`.local-data/gateway-policy/off-diagnosis/router-wire.json`。证据只保存合成输入与响应，不含鉴权请求头。

## 模板与工具字段控制实验

使用 [Qwen 官方模板](https://huggingface.co/Qwen/Qwen3.8-27B/raw/main/chat_template.jinja) 渲染相同工具历史，并保持 enable_thinking=false。模板以已闭合的 `<think>\n\n</think>` 前缀开始生成。通过 `/v1/completions` 提交渲染后的文本，绕过 Chat 接口的模板处理和工具约束逻辑。

初始无 strict 字段的官方模板输入为 352 token，真实 Chat 请求为 357 token。进一步检查确认：SGLang 的 [Function 协议模型](https://github.com/sgl-project/sglang/blob/v0.5.10/python/sglang/srt/entrypoints/openai/protocol.py#L486) 默认定义 `strict: bool = False`；[工具序列化](https://github.com/sgl-project/sglang/blob/v0.5.10/python/sglang/srt/entrypoints/openai/serving_chat.py#L342) 使用 `item.model_dump()`，将默认值加入工具字典。官方模板将整个工具字典序列化为文本，因而这个字段进入模型输入。

补上同样字段后，官方模板输入也变成 357 token，重复回答随之复现。因此最初“可能模板文件过旧”的推断没有成立，不能作为根因。

固定输入、模型、采样参数及非思考前缀；分别测试种子 1、2，并交叉调整工具字段排列顺序：

| 模型可见工具定义 | 测试数 | 含结束标签及重复回答 |
| --- | ---: | ---: |
| 无 strict 字段，两种字段顺序 | 4 | 0 |
| strict:false，两种字段顺序 | 4 | 4 |
| strict:true，一种字段顺序 | 2 | 0 |

strict:true 仅用于控制实验，不代表建议强制开启严格工具模式。实验使用文本 completion 接口，字段在这里是模型输入文本，不是实际启用的工具约束。

其他对照：关闭 preserve_thinking、关闭 separate_reasoning、保留特殊 token，均仍能复现。指定独立 cache_salt 后，strict:false 文本输入的两个种子仍异常，无 strict 的两个种子正常；Chat 接口两个种子一异常一正常。未取得缓存 token 明细，不能由此声称排除所有缓存问题，也不能把小样本比例当成线上故障率。

证据：`schema-factorial.json`、`cache-isolation.json`、`normalized-completion-False.json`、`completion-False.json`，均在上述本地证据目录。

## 为什么作为正文显示

[SGLang v0.5.10 reasoning parser](https://github.com/sgl-project/sglang/blob/v0.5.10/python/sglang/srt/parser/reasoning_parser.py) 在非思考状态下，若生成内容没有 `<think>`，一次性解析直接将全部内容返回 normal_text。流式路径也仅在思考状态中处理结束标签。

从对应源码通过 AST 原样提取 StreamingParseResult 和 BaseReasoningFormatDetector，将本次捕获的异常回答分别一次性和逐字符回放：两者均返回完整的两段回答及 `</think>`，reasoning_text 为空。证据：`parser-replay.json`。

所以 reasoning_content 为空不能证明模型没有产生思考格式残留。关闭思考在当前路径中通过模板前缀引导生成，并不等于对输出标签实施硬性禁止。此前针对思考模式中工具调用隐式结束的解析修复，也不能直接解决这个非思考状态下的孤立结束标签问题。

## 修复方向与边界

优先在上游工具模板边界区分协议控制字段与模型需要的工具说明，保留 strict 的协议语义，但避免默认控制字段无差别进入模型可见工具文本。网关本来没有发送 strict，仅在网关删除字段不能阻止 SGLang 再次补入。

这一方向应先通过更多工具、工具回传和多轮场景验证，并核对该模型的工具模板约定，再决定实现。当前证据支持该方向，尚不构成完整修复通过的结论。

不建议提高预算、强制所有工具 strict:true，或依靠正文删标签与去重掩盖异常。结束标签前的内容究竟属于正文还是异常推理，在没有正确生成协议的情况下不能靠字符串位置安全判断。若后续实施涉及上游模型服务，需要另行明确该环境的修改范围；本轮没有更改它。

### 已用部署文件确认的结论

1. 实际模板与对照模板一致，文件 SHA256 仅保存在本地忽略证据中。因此“模板拿错或过旧”没有依据。
2. 实际 serving_chat.py 和 reasoning_parser.py 与本次对照所用 v0.5.10 源码完全一致。实际 protocol.py 第 529 行定义 `strict: bool = False`；serving_chat.py 第 352 行将 model_dump() 的工具结构交给模板。
3. 从部署源码原样提取 Function、Tool、Qwen3Detector 及其基类，本地离线回放真实捕获的合成样例：未带 strict 的输入确实被补成 strict:false；一次性与逐字符解析均把两段回答和结束标签返回为正文。证据：`.local-data/gateway-policy/upstream-ssh/deployed-source-replay.json`。
4. 启动命令和只读状态均确认 `disable_radix_cache=true`。这进一步削弱了将本次现象归因为跨请求 radix 前缀缓存污染的解释；不能据此证明不存在其他推理引擎数值问题。

### 新发现的实现差异与验证边界

模型 config.json 中 `text_config.mamba_ssm_dtype` 声明为 float32，但实际启动显式覆盖为 bfloat16。这是 GDN/SSM 递归状态精度，不能与模型权重本身的 BF16 混为一谈。官方部署说明允许相应精度选择，但要求将 BF16 的准确性作为工作负载验收项。因此这是需要隔离实例做同输入对照的数值精度变量，尚未证明导致本次重复回答。只读授权下没有切换精度或重启服务。

当前服务还设置 TP=4、chunked_prefill_size=65536、max_prefill_tokens=65536、max_running_requests=256、linear_attn_backend=triton。这些是后续性能分析的事实基线，不是已证实的故障原因；本次没有做负载测试，也不能把配置上限当作实际并发能力。

[SGLang 的 Qwen3.8 官方部署说明](https://docs.sglang.io/cookbook/autoregressive/Qwen/Qwen3.8-27B) 当前指定提交 `1cf2b8c54d81802abc15dcf23a29b9cc687bc01e` 或相应专用镜像。实际服务的旧解析器缺少新版 Qwen 对 `<tool_call>` 隐式结束思考的处理。这支持在隔离部署中采用官方模型适配基线进行对照，但不能承诺一次升级就修复非思考模式中的所有异常。

建议顺序：先用官方适配基线和模型声明的状态精度建立隔离对照，再检验非思考工具回传及 strict 字段触发是否仍存在；最后才决定是否需要调整工具模板序列化。这样可以避免在旧引擎上针对单个样例叠加补丁。本轮没有实施这些变更。
