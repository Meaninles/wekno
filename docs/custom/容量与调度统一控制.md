# 容量与调度统一控制

> 适用代码基线：当前工作区，核对日期 2026-08-01。

## 1. 目标与入口

系统管理员在“设置 → 平台 → 容量与调度”管理实际模型路由。该页面独立于“模型管理 / 衍生任务模型”，API 前缀为：

```text
/api/v1/custom/capacity-control
```

`GET /effective` 返回所有配置的编译后有效值、模型绑定、模块 fan-out、运行角色消费槽位和冲突；`POST /validate` 只校验并规范化输入，不写数据库。资源池、模板、绑定、审计和队列状态使用同一前缀。

## 2. 唯一并发真源

一个实际模型路由只有一个资源池。管理员直接配置：

| 字段 | 含义 |
|---|---|
| `max_inflight` | 该实际路由的全集群供应商调用总并发，也是绑定聊天模型的执行会话并发 |
| `interactive_reserve` | 从后台占用中保留给交互请求的槽位 |
| `tenant_burst` | 单租户在该资源池的上限 |
| `document_burst` | 单文档在该资源池的上限 |
| `rpm` / `tpm` | 实际路由请求/Token 预算；0 表示不启用该维度 |
| `chat_max_waiting` | 聊天等待室大小；`null` 继承平台等待默认值 |

编译关系固定为：

```text
background_max = max_inflight - interactive_reserve
document_burst <= tenant_burst <= max_inflight
document_burst <= background_max
chat_sessions = max_inflight
```

因此 `max_background_inflight` 只是服务端物化值，不再是独立输入。旧的 `chat_max_concurrent`、`tenant_guaranteed`、`document_guaranteed` 和 `token_burst` 会在保存时清理为规范值。`derivative.tpm`、`derivative.concurrency`、`chat.queue.default_max_concurrent` 旧系统设置不再参与运行时决策，也不再作为可写设置展示。

## 3. 上下游如何匹配

- 模型包装器在每次真实供应商调用前读取模型绑定和资源池，Redis 在所有 API/worker 副本之间执行总量、后台、租户、文档和 RPM 准入。
- 聊天 FIFO 的执行会话数直接使用资源池 `max_inflight`；平台聊天设置只控制开关、等待室和单用户公平性。
- Wiki 引用、Graph 实体、Graph 关系和问题批次通过 admission-aware 模型包装器读取有效文档额度，本地 `errgroup` fan-out 会先收敛到该额度；Redis 准入仍是最终权威。
- `WEKNORA_ASYNQ_TASK_CONCURRENCY`、Wiki worker concurrency 和副本数是消费槽位，不是模型容量。它们可以大于资源池额度，多余任务在调度器内等待，不会把供应商并发乘大。
- 模板只用于新识别或“恢复默认”的资源池，不覆盖已手工修改的活动资源池。
- 配额池和网关池是可选高级维度；为空时不创建隐含限制。同一实际路由指纹绑定到多个资源池会被有效值报告判为错误。

## 4. 等待、失败和重试

普通后台容量饱和时，`modeladmission` 在任务 context 内等待，不再立即返回业务错误。只有显式配置有限后台等待或可持久让出的 TPM/配额等待才返回 typed deferral；Asynq 将其视为不消耗失败次数的调度延期。

Wiki citation 不把 typed deferral 计入失败批次；Graph 关系抽取也会向持久任务传播 deferral，而不是吞掉后以不完整关系图成功。供应商真实 transport/429/5xx、结构化输出错误和持久化错误仍按各自有限业务预算处理。

## 5. 冲突校验

写接口会拒绝：

- `interactive_reserve >= max_inflight`；
- 租户上限超过总并发；
- 文档上限超过租户上限或有效后台并发；
- 非法 RPM/TPM、熔断、超时或状态值；
- 旧 `policy_version` 的并发写入。

`GET /effective` 还报告数据库中遗留的无效设置、同一路由拆到多池、一个池混入多个实际路由、无绑定池和模块 fan-out 收敛。`healthy` 只由 error 级冲突决定，warning/info 不会阻断运行。

## 6. 验收

自动测试覆盖规范化、冲突矩阵、后台等待、有限让出、聊天单真源、Wiki deferral 和路由拆池。无模型费用的 API 验收脚本为：

```powershell
pwsh -ExecutionPolicy Bypass -File custom/tests/capacity_control_e2e/api_capacity_control.ps1
```

脚本创建一个无绑定临时资源池，依次验证 1/2/8 并发组合、热更新、多 API 副本回读、非法组合、乐观锁和旧端点移除，最后排空删除临时池并恢复本地管理员密码哈希。
