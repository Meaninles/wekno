# 容量与调度统一控制

> 适用代码基线：当前工作区，核对日期 2026-08-01。

## 1. 目标与入口

系统管理员在“设置 → 平台 → 容量与调度”管理实际模型路由。该页面独立于“模型管理 / 衍生任务模型”，API 前缀为：

```text
/api/v1/custom/capacity-control
```

`GET /effective` 返回所有配置的编译后有效值、模型绑定、模块 fan-out、在线实例、实时 Redis 租约和冲突；`POST /validate` 只校验并规范化输入，不写数据库。资源池、模板、绑定、审计和队列状态使用同一前缀。全局后台调度策略使用 `GET/PUT /scheduler-policy`，按 `policy_version` 乐观锁热更新。

## 2. 唯一并发真源

一个实际模型路由只有一个资源池。管理员直接配置：

| 字段 | 含义 |
|---|---|
| `max_inflight` | 该实际路由的全集群供应商调用总并发，也是绑定聊天模型的执行会话并发 |
| `interactive_reserve` | 从后台占用中保留给交互请求的槽位 |
| `tenant_burst` | 单租户在该资源池的上限 |
| `document_burst` | 单文档在该资源池的上限 |
| `rpm` / `tpm` | 实际路由请求/Token 预算；0 表示不启用该维度 |
| `chat_max_waiting` | 聊天等待室大小；`null` 继承平台等待默认值 |

编译关系固定为：

```text
background_max = max_inflight - interactive_reserve
document_burst <= tenant_burst <= max_inflight
document_burst <= background_max
chat_sessions = max_inflight
```

因此 `max_background_inflight` 只是服务端物化值，不再是独立输入。旧的 `chat_max_concurrent`、`tenant_guaranteed`、`document_guaranteed` 和 `token_burst` 会在保存时清理为规范值。`derivative.tpm`、`derivative.concurrency`、`chat.queue.default_max_concurrent` 旧系统设置不再参与运行时决策，也不再作为可写设置展示。

## 3. 上下游如何匹配

- 模型包装器在每次真实供应商调用前读取模型绑定和资源池，Redis 在所有 API/worker 副本之间执行总量、后台、租户、文档和 RPM 准入。后台耐久任务先持有一个任务级 work lease；同一任务内的串行或并行模型调用复用该 lease，不会按调用数重复占用执行窗口。
- 聊天 FIFO 的执行会话数直接使用资源池 `max_inflight`；平台聊天设置只控制开关、等待室和单用户公平性。
- Wiki 引用、Graph 实体、Graph 关系和问题批次通过 admission-aware 模型包装器读取有效文档额度，本地 `errgroup` fan-out 会先收敛到该额度；Redis 准入仍是最终权威。
- `WEKNORA_ASYNQ_TASK_CONCURRENCY`、Wiki worker concurrency 和副本数只是进程安全上限，不是模型容量。全局执行窗口与实例数量无关，多余任务留在耐久队列或无损延期，不会把供应商并发乘大。
- 模板只用于新识别或“恢复默认”的资源池，不覆盖已手工修改的活动资源池。
- 配额池和网关池是可选高级维度；为空时不创建隐含限制。同一实际路由指纹绑定到多个资源池会被有效值报告判为错误。

## 4. 全局后台执行窗口与公平性

每个实际模型资源池独立计算：

```text
B = max_inflight - interactive_reserve
P = B × prefetch_factor
```

`B` 是供应商后台硬并发，`P` 是允许进入执行态的耐久任务（Wiki 按独立文档 Map 计数）全局窗口。默认 `prefetch_factor=2`。以 `B=3` 为例，无论运行 2、4 还是 10 个 worker 实例，同一池最多只有 6 个已派发/执行中的耐久任务、3 个真实供应商调用。任务内部即使有两个模型子调用也仍只占一个 task work lease。

默认衍生任务与 Wiki 权重为 `2:1`。两侧都有积压时，`B=3` 的供应商份额为 `2:1`，`P=6` 的执行窗口份额为 `4:2`；任一侧没有等待者时，另一侧可借用全部容量。等待者标记和 active lease 都是带 TTL 的 Redis 有序集合，实例宕机不会永久占槽。

任务获得 work lease 后，模型子调用最多等待 `background_max_wait_seconds`（默认 30 秒）获得供应商容量。超时返回 typed deferral，由 derivative/Wiki 的耐久状态机延期重投：不增加供应商调用次数、不消耗业务失败预算、不增加用户看到的“解析次数”。未获得任务 work lease 的 worker 同样立即无损让出，不进入模型等待。

derivative 和 Wiki Map 都使用 PostgreSQL-authoritative outbox。derivative 在 `custom_derivative_work_items` 保存派发 epoch/lease；Wiki Map 在 `task_pending_ops` 保存资源池、下次尝试时间、派发 epoch/lease。两套 dispatcher 使用同一资源池 advisory transaction lock，在同一事务里合计两张表的有效租约，因此 `P` 是真正的跨队列全集群上限，而不是两个队列各自一份上限。两侧有积压时各自保护 `4:2` 份额，另一侧无到期任务时可借满 6 个槽。物化和 finalizer 不占模型执行窗口；Redis/Asynq 只承载可丢弃的 wake，不再镜像完整 Wiki backlog。

表格元数据摘要也属于 derivative outbox（`work_kind=datatable_metadata`）。核心 DocReader、分块和索引完成后，postprocess 先持久化表格/摘要/问题/图谱/Wiki 的精确意图和代次回执，再立即把 `parse_status` 提交为 `completed`。这些可选任务继续更新 `enrichment_status`、`wiki_status` 和计数，但不能把正文重新变成“解析中”或“解析失败”。

调度热配置只有五项：

| 字段 | 默认 | 含义 |
|---|---:|---|
| `prefetch_factor` | 2 | 执行窗口相对后台硬并发的倍数 |
| `derivative_weight` | 2 | 衍生任务公平权重 |
| `wiki_weight` | 1 | Wiki 公平权重 |
| `background_max_wait_seconds` | 30 | 一次容量等待上限，超时无损延期 |
| `dispatch_lease_seconds` | 120 | derivative/Wiki Map 重复唤醒抑制租约 |

`custom_runtime_instances` 每 10 秒记录 API、解析、衍生、Wiki、maintenance 等实例心跳和各能力的本地并发安全上限，35 秒未心跳即从在线报告剔除。该表只负责可观测性与软均衡；Redis 执行窗口、PostgreSQL 任务租约和 epoch fencing 才是正确性边界。

## 5. 等待、失败和重试

普通后台容量饱和时，`modeladmission` 只在有限窗口内等待，然后返回 typed deferral；Asynq 和耐久状态机将其视为不消耗失败次数的调度延期。真实供应商请求只有在任务持有 work lease、当前调用再获得 provider lease 后才开始。

Wiki citation 不把 typed deferral 计入失败批次；Graph 关系抽取也会向持久任务传播 deferral，而不是吞掉后以不完整关系图成功。供应商真实 transport/429/5xx、结构化输出错误和持久化错误仍按各自有限业务预算处理。

## 6. 冲突校验

写接口会拒绝：

- `interactive_reserve >= max_inflight`；
- 租户上限超过总并发；
- 文档上限超过租户上限或有效后台并发；
- 非法 RPM/TPM、熔断、超时或状态值；
- 旧 `policy_version` 的并发写入。

`GET /effective` 还报告数据库中遗留的无效设置、同一路由拆到多池、一个池混入多个实际路由、无绑定池和模块 fan-out 收敛。`healthy` 只由 error 级冲突决定，warning/info 不会阻断运行。

```powershell
pwsh -ExecutionPolicy Bypass -File custom/tests/capacity_control_e2e/api_capacity_control.ps1
```

脚本创建一个无绑定临时资源池，依次验证 1/2/8 并发组合、热更新、多 API 副本回读、非法组合、乐观锁和旧端点移除，最后排空删除临时池并恢复本地管理员密码哈希。
