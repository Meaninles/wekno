# 当前版本生产停机更新部署执行手册

> 状态（2026-08-06）：本轮生产更新已完成。本文从第 3 节起是以后重新发布或回滚时
> 使用的执行剧本，不代表现在应继续执行。当前生产事实以
> [当前生产实现与部署基线](./当前生产实现与部署基线.md)为准。仅代码/文档同步不得
> 执行本手册中的停机、备份、迁移、apply、重启或知识库重建命令。

本文适用于现有 `weknora` 命名空间和 `knora.moutai.com.cn`。本次采用完全停机
更新，复用全部现有资源；不新增节点、存储、数据库、Redis 或模型服务。

以后重新执行时，第 4 节起会中断业务，必须获得明确发布窗口授权。执行人必须保存
命令输出、时间、Git SHA、镜像 digest、cutoff、备份、恢复演练和验收报告。

## 1. 不可变更的发布原则

1. 先切断业务 Ingress 路由，再停止全部 API、解析、衍生、Wiki、DocReader 和
   Agent。可以调整业务 Ingress 对象，但禁止删除 `ingress-nginx`、Ingress
   Controller、其 Service 或集群级入口组件。
2. 最终 cutoff 必须在所有可写 Pod 退出后生成；初步盘点不能替代最终 cutoff。
3. 只备份 PostgreSQL。生产源文件已经在私有 OBS，`/data/files` 无持久数据；不做
   文件备份、文件路径迁移或 Neo4j 备份。
4. 原知识库和原 `obs://` 对象保持不变。混合库新建独立纯文档库，旧库保留到验收
   和回退期结束。
5. 不回放旧 Asynq payload、dead letter 或衍生任务。失败/未完成文档通过知识库整体
   重建恢复；旧 generation、已删除目标和终态记录全部只作审计。
6. 迁移 Job 只能有一个，`AUTO_MIGRATE=true` 只能出现在该 Job。
7. 运行镜像和 sandbox 镜像必须用 `@sha256:` 固定；禁止仅凭 tag 发布。
8. 验收失败时保持 Ingress 关闭，不允许带病开放流量。

## 3. 不停机发布准备

### 3.1 建立发布目录

在生产运维机的已审核代码目录执行：

```bash
set -euo pipefail

export RELEASE_ID="<change-id>-$(date +%Y%m%d-%H%M%S)"

git rev-parse HEAD

install -d -o root -g root -m 0700 /root/weknora-secure "$CUTOFF_ROOT"
```

### 3.2 构建并固定镜像

从同一个批准提交构建并推送 app、DocReader、frontend、mobile-web、general-agent 和
document-processing-agent。sandbox 相对现网构建提交没有源码差异，本次复用已固定且
三节点 smoke 通过的 digest；不得把 sandbox tag 当成运行身份。把 registry 返回的
64 位 digest 填入 `$SITE_VALUES`，不得混用提交。

生产节点不能访问 Docker Hub，必须使用现网已经验证的
`docker.m.daocloud.io/library` 拉取以下精确 tag，再固定到项目 SWR 的 `base/`
命名空间；不要把现网运行镜像拼接成不可复现的发布镜像：

```text
golang:1.26-bookworm
debian:12.12-slim
python:3.10.18-bookworm
python:3.11-slim
node:22-alpine
nginx:stable-alpine
```

构建中其余依赖也必须在不停机准备阶段预热：腾讯 APT/PyPI/npm、goproxy、npmmirror
Playwright 和 ghfast GitHub proxy。protoc、grpc health probe 以及版本一致的 DuckDB
`spatial/excel` 扩展会写入受控构建上下文并记录 SHA；Python/Go/npm/Playwright 依赖在
镜像构建层中缓存。停机阶段只拉最终镜像 digest，不再下载构建依赖。

`.1` 的 Docker 18.09 不支持 `RUN --mount=type=cache`。脚本会为旧构建器生成经过审计的
临时 Dockerfile，只移除三处 Go module cache mount 前缀，不修改仓库源码。默认仅做
失败关闭的预检；基础镜像和空间全部满足后才加 `--execute`。构建串行执行，单次上限
2 CPU/10 GiB，进程使用较低 CPU/IO 优先级：

```bash
export RELEASE_SHA="$(git rev-parse HEAD)"
export IMAGE_TAG="${RELEASE_SHA:0:10}-prod-20260804"
export BUILD_ROOT="/mnt/weknora-data/weknora-builds/$IMAGE_TAG"
export IMAGE_OUT="$BUILD_ROOT/image-output"
export DEPENDENCY_OUT="$BUILD_ROOT/dependency-preload"
export REGISTRY=swr.cloud-mt-1.moutai.com.cn/ap-weknora-swr-zhengshi-01
export CURRENT_APP_IMAGE="$REGISTRY/weknora-app:846e38ba6-vlm-queue-20260730"

bash "$BUILD_ROOT/source/deploy/production/preload-build-dependencies.sh" \
  --source-dir "$BUILD_ROOT/source" --registry "$REGISTRY" \
  --output-dir "$DEPENDENCY_OUT" --duckdb-source-image "$CURRENT_APP_IMAGE"

# 预检 PASS 后执行依赖预热；会写 packages/，因此随后重新生成构建上下文 hash。
bash "$BUILD_ROOT/source/deploy/production/preload-build-dependencies.sh" \
  --source-dir "$BUILD_ROOT/source" --registry "$REGISTRY" \
  --output-dir "$DEPENDENCY_OUT" --duckdb-source-image "$CURRENT_APP_IMAGE" \
  --execute

bash "$BUILD_ROOT/source/deploy/production/build-release-images.sh" \
  --source-dir "$BUILD_ROOT/source" \
  --registry "$REGISTRY" --tag "$IMAGE_TAG" \
  --output-dir "$IMAGE_OUT" --legacy-builder

# 预检 PASS 后才执行；每个镜像之间复核业务 Pod 和节点余量。
bash "$BUILD_ROOT/source/deploy/production/build-release-images.sh" \
  --source-dir "$BUILD_ROOT/source" \
  --registry "$REGISTRY" --tag "$IMAGE_TAG" \
  --output-dir "$IMAGE_OUT" --legacy-builder --execute
```

`base-images.tsv`、`packages/SHA256SUMS.release`、`image-digests.env`、
`app-skills-preloaded.aggregate.sha256`、完整构建日志和临时 Dockerfile diff 均属于
发布证据。任何镜像/依赖源缺失、package hash 错误、smoke 失败或推送后拿不到
`sha256:` digest 都必须停止，不能进入停机窗口。

```bash
grep -n 'REPLACE_' "$SITE_VALUES"
grep -n 'digest:' "$SITE_VALUES"
```

第一条在正式渲染前必须无输出；sandbox 必须是完整 `repository@sha256:digest`。

## 4. 正式停机和最终回滚点

### 4.1 关闭入口并停止所有业务进程

```bash
kubectl -n "$NS" get ingress weknora -o yaml \
  >"$CUTOFF_ROOT/${RELEASE_ID}-ingress-before.yaml"
kubectl -n "$NS" delete ingress weknora

for deployment in \
  weknora-app weknora-docreader \
  weknora-general-agent weknora-document-processing-agent \
  weknora-custom-general-agent weknora-custom-document-processing-agent \
  weknora-frontend weknora-mobile-web
do
  if kubectl -n "$NS" get deployment "$deployment" >/dev/null 2>&1; then
    kubectl -n "$NS" scale deployment "$deployment" --replicas=0
  fi
done

kubectl -n "$NS" get deployment -o name \
  | grep '^deployment.apps/weknora-app-' \
  | xargs -r -n1 kubectl -n "$NS" scale --replicas=0
kubectl -n "$NS" get pod -o wide
```

等待上述 Pod 全部退出。不要删除 PostgreSQL、Redis、Neo4j、LiteLLM 或 OBS Secret。

旧 app 全部退出后、运行迁移 Job 前，启用已验证的技能 staging。脚本会先对三个节点
统一预检，再同盘原子改名；任一节点失败会自动恢复已经切换的节点：

```bash
export RELEASE_SHA='<最终发布记录中的 40 位提交 SHA>'
export IMAGE_TAG="${RELEASE_SHA:0:10}-prod-20260804"
bash deploy/production/switch-preloaded-skills.sh "$IMAGE_TAG" --check
bash deploy/production/switch-preloaded-skills.sh "$IMAGE_TAG" --apply
bash deploy/production/switch-preloaded-skills.sh "$IMAGE_TAG" --check
```

最后一条必须在三节点都返回 `SKILLS_STATE=active` 后才能继续。旧技能保留在同盘
`.preloaded-rollback-$IMAGE_TAG`，不得在回退期内删除。

### 4.2 最终 cutoff、数据库备份和完整恢复演练

```bash
bash deploy/production/capture-release-cutoff.sh \
  "$RELEASE_ID" --output-root "$CUTOFF_ROOT"

(cd "$CUTOFF_ROOT/$RELEASE_ID" && sha256sum -c SHA256SUMS)

bash deploy/production/backup-postgres.sh "$RELEASE_ID"
bash deploy/production/verify-postgres-restore.sh "$RELEASE_ID"
```

备份写入 `.7:/mnt/weknora-data/weknora-db-backups/$RELEASE_ID/WeKnora.dump`。脚本会验证
cutoff hash、远端文件 hash、`pg_restore --list`，再在现有 PG 建临时数据库完整恢复，
核对 schema、知识库数和文档数后删除临时库。三步任何一步失败都停止发布。

不备份 OBS 或 `/data/files`；回退依靠发布前数据库和未改动的原 OBS 对象。

## 5. 平台迁移和门控启动

### 5.1 修复 PostgreSQL 运行资源

```bash
kubectl -n "$NS" patch deployment weknora-postgres \
  --type strategic \
  --patch-file deploy/production/postgres-runtime.strategic-merge.yaml
kubectl -n "$NS" rollout status deployment/weknora-postgres --timeout=10m
kubectl -n "$NS" exec deployment/weknora-postgres -- df -h /dev/shm
kubectl -n "$NS" logs deployment/weknora-postgres --since=15m \
  | grep -F 'could not resize shared memory segment' && exit 1 || true
```

结果必须为 request `3C/8Gi`、limit `6C/12Gi`、`/dev/shm` 至少 2Gi，且无新的共享
内存错误。

### 5.2 唯一迁移 Job

```bash
kubectl -n "$NS" apply -f "$RENDER_DIR/migration-job.yaml"
export MIGRATION_JOB="$(kubectl -n "$NS" create --dry-run=client \
  -f "$RENDER_DIR/migration-job.yaml" -o name)"
kubectl -n "$NS" wait --for=condition=complete \
  "$MIGRATION_JOB" --timeout=2h
kubectl -n "$NS" logs "$MIGRATION_JOB"

kubectl -n "$NS" exec deployment/weknora-postgres -- \
  sh -c 'psql -X -At -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  -c "SELECT version,dirty FROM schema_migrations"'
```

schema 必须为 `95|f`。

```bash
unset WEKNORA_ADMIN_TOKEN
kill "$PORT_FORWARD_PID"
```

脚本必须从计划中唯一匹配全部七个生产模型池，先逐池调用 validate，再使用 If-Match
更新 scheduler 和资源池并执行 reconcile。任一模型缺失、重名、类型不符、证据不是
verified 或 effective 返回 error，均必须停止发布；不能把模型服务启动上限当成实测能力。

### 5.4 先关闭待重建混合源库的 Wiki

按 `knowledge-base-rebuild-tracker.csv` 中 31 条
`CREATE_NON_WIKI_REPLACEMENT_AND_REINGEST` 操作。对每个租户使用有权限的 Owner/Admin
会话：

1. GET 原库完整配置并留存响应；
2. PUT 原库时提交完整 mutable config，只把 `indexing_strategy.wiki_enabled` 改为
   false；不能只提交局部 config，否则会把切分/图片配置清零；
3. 不删除原 Wiki 页面，不删除原库；
4. 复查数据库配置为 false 后，在 tracker 写 `source_wiki_disabled=YES`。

所有 31 个源库关闭后，才允许启动 Wiki worker。

### 5.5 启动最终拓扑并做平台验收

```bash
kubectl -n "$NS" apply -f "$RENDER_DIR/workloads.yaml"
kubectl -n "$NS" rollout status deployment/weknora-app --timeout=15m
kubectl -n "$NS" get deployment,pod -o wide

python3 deploy/production/verify-release.py platform \
  "$RELEASE_ID" "$CUTOFF_ROOT/$RELEASE_ID"
```

platform 验收必须在创建 31 个新目标库之前执行，因为它会用 cutoff 核对原始 59 个
库和最终 cutoff 文档数（2026-08-04 在线预检为 2,635）。它还核对固定节点、digest、Pod restart、所有 role `/ready`、
迁移 Job、PG `/dev/shm`、schema、数据库连接和模型容量。

## 6. 知识库重建

### 6.1 共同规则

- 每个 API 动作按 `tenant_id` 使用该租户 Owner/Admin 身份；Token 不落 Git/台账。
- tracker 初始副本带 SHA，工作副本允许填写；不得改初始 CSV。
- 所有批量 reparse 每次最多 200 个文档 ID。
- 不提交 task ledger 中的旧 payload；`task-recovery-manual-tracker.csv` 正常应只有表头。
- 新目标库必须保留原库的 description、embedding/summary/derivative、vector store、
  chunking、VLM、音频、storage、extract/graph 和 question-generation 配置，只取消
  Wiki；模型统一改为当前管理员下发目录，不能复制已下架的 ASR 或旧私有模型。
- 即使文档全部完成，只要库内向量来自早期 2048 维截断模型，也必须进入全量重建，
  使用当前 Qwen3-Embedding-8B 的 4096 维输出重新生成全部向量并验证真实召回。
- 标签按名称/颜色/排序重建，文档标签按新 tag ID 重绑；文件夹按 path 从浅到深
  重建，文档按新 folder ID 放回原路径。

### 6.2 8 个纯文档库原地重建

对 `REBUILD_DOCUMENT_KB_IN_PLACE` 的 8 个库：

1. 从 `knowledge-rebuild-documents.csv` 取得该库全部文档 ID，不只取失败文档；
2. 每 200 个调用 `/api/v1/knowledge/batch-reparse`；
3. 记录每批新 task ID，写 `batch_reparse_submitted=YES`；
4. 等待 777 篇全部满足完全成功，disabled 必须从失败态收敛为 0。

### 6.3 31 个混合库新建纯文档目标

每个源库严格按下列顺序：

1. 使用第 5.4 节保存的完整配置创建显式 target；`type=document`，
   `wiki_enabled=false`，不带 Wiki config，名称使用 tracker 的 target 名。不要用 copy
   接口的空 target 快捷模式，因为它不会完整复制音频/图谱/问题生成配置。
2. 把新 target ID/name 写入 tracker；确认 vector store 和 storage backend 与源库
   相同，embedding 使用当前下发的 Qwen3-Embedding-8B，不能沿用旧 2048 维配置。
3. 按 `knowledge-folder-inventory.csv` 的 depth/path 从浅到深创建 176 个文件夹并保存
   `source_folder_id -> target_folder_id` 映射；无文件夹的库也需审计后写
   `folders_recreated=YES`。
4. 在 target 创建源库全部标签，保存 `source_tag_id -> target_tag_id` 映射。
5. 调用 `/api/v1/knowledge-bases/copy`，显式传 source_id 和 target_id；等待 progress
   completed。在线预检中该步骤只会真正克隆 parse 已完成的 1,035 篇文档（包括 2 篇无源路径但
   已有 chunks 的文档）。完成后核对 target 文档数等于该库 cutoff 的
   `parse_completed`，写 clone task ID 和 `source_seed_complete=YES`。
6. 对 cutoff 中 `DOWNLOAD_ORIGINAL_AND_UPLOAD_TO_REPLACEMENT` 的文档（在线预检为 629 篇），从源
   `/knowledge/{id}/download` 下载原件后上传 target；沿用文件名、解析配置、新 tag
   ID 和新 folder ID。源 OBS 路径不改。每个上传返回的新文档 ID必须记录；全部提交
   后写 `missing_sources_reingested=YES`。
7. 对已 clone 的文档（在线预检为 1,035 篇）按 target 新 ID、每批最多 200 调用 batch-reparse；
   新上传的文档已经是一次全新解析，不重复提交。写
   `batch_reparse_submitted=YES`。
8. 将 cutoff 中的 Agent（在线预检为 6 个）和 1 个定时聊天中的源 KB ID替换为 target ID；为 target 复制 2
   条组织共享和 1 个用户置顶。若最终 cutoff 新出现 data source/IM/session 引用，
   按 `knowledge-base-reference-inventory.csv` 的 required_action 逐项重绑。源 share/pin
   可保留用于回退，Agent/定时任务不得继续指向源库。写
   `external_references_rebound=YES`。
9. 不删除源库、不删除源文档、不删除源 Wiki 页面。源库改名或后续下线要等业务
   验收和回退期结束后另开变更。

最终每个 target 应有最终 cutoff 对应文档（在线预检合计 1,664 篇）、0 disabled、0 Wiki page、0
非终态工作流，并与源库具有相同的非 Wiki 配置、标签和文件夹路径。

### 6.4 全部成功库和空库

`KEEP_ALL_COMPLETE` 只适用于全部文档成功、工作流一致且向量已经是当前 4096 维的
库；空库可以保留。旧 2048 维库即使页面显示全部完成也不能保留，必须重建。历史
failed/terminal 记录只有在当前 generation、索引与真实召回均正常时才不触发重建。

## 7. 验收和开放流量

### 7.1 自动验收

所有 tracker 行填完后：

```bash
python3 deploy/production/verify-release.py final \
  "$RELEASE_ID" "$CUTOFF_ROOT/$RELEASE_ID"
```

脚本必须同时证明：

- 所有 Pod 固定分布、Ready、digest 正确、无重启；PG 和迁移正常；
- 39 个重建库全部完成，31 个 target 是纯 document、无 Wiki、disabled=0；
- 最终 cutoff 中全部源文档（在线预检为 2,635 篇）的 `file_hash`、`file_path` 和存活状态未变；
- target 非 Wiki 配置、标签、文档标签、176 个文件夹层级和 cutoff 文档位置一致；
- Agent/定时任务已切换，share/pin 已复制，其他活动引用完成重绑；
- 没有真正非终态工作流；历史 failed 终态允许保留；人工旧任务重放为 0。

### 7.2 业务 smoke

Ingress 仍关闭，通过 port-forward 完成：

1. API 登录、租户切换、知识库列表；
2. 每个 target 至少一个真实问题召回，核对文档标题、片段和权限；
3. Agent 使用已切换 target 回答；定时任务先手工触发一次；
4. 组织共享账号能看到目标库；置顶用户视图正常；
5. 文件夹树、标签筛选、文档下载一致；
6. 普通 PDF、含图 PDF/VLM、音频 ASR、一个大文件分片、一个失败重试样例；
7. frontend 和 `/mobile/`；三个 API/parse/DocReader 副本实际分流；
8. 连续观察日志、Pod restart、DB active connections、模型 effective inflight。

每个库在 tracker 填 `retrieval_verified=YES`、`owner_accepted=YES`。全部通过后才恢复
入口：

```bash
kubectl -n "$NS" apply -f "$CUTOFF_ROOT/${RELEASE_ID}-ingress-before.yaml"
kubectl -n "$NS" get ingress weknora -o wide
curl -fsS https://knora.moutai.com.cn/health
```

## 8. 回退

### 8.1 数据库迁移前

若尚未执行迁移 Job，可在 Ingress 关闭、所有新 Pod 为 0 时恢复 cutoff 中的旧
Deployment/Service/Ingress 和旧 digest；不需要数据库恢复。若技能已经切换，先执行：

```bash
bash deploy/production/switch-preloaded-skills.sh "$IMAGE_TAG" --rollback
```

三节点必须都返回 `SKILLS_STATE=rolled-back`，再启动旧 app。

### 8.2 已执行迁移或知识库重建后

不能只回滚镜像。保持 Ingress 不存在、全部业务 Deployment 为 0，然后：

```bash
bash deploy/production/restore-postgres-backup.sh \
  "$RELEASE_ID" --confirm-stop-the-world-restore

bash deploy/production/switch-preloaded-skills.sh "$IMAGE_TAG" --rollback
```

脚本先校验备份 hash 和恢复演练，拒绝有业务 Pod或 Ingress 时执行；把当前
`WeKnora` 改名保留为 `weknora_postrelease_<hash>` 且禁止连接，再恢复发布前数据库。
恢复失败会自动换名回原库。确认 schema、59 个库和最终 cutoff 文档数后，再部署 cutoff
中的旧清单和 digest。技能回滚也必须在所有业务 Pod 为 0 时执行，并在三节点都返回
`SKILLS_STATE=rolled-back` 后再启动旧 app。

Redis/Asynq 不作旧 payload 回放。回退启动消费者前先只起 API，确认 generation
fence 会丢弃发布期间的陈旧任务；若旧版本不具备该能力，保持消费者为 0，由运维
审阅 `redis-asynq-key-inventory.csv` 后另行清理精确 Asynq 前缀，禁止 `FLUSHDB`。
需要恢复的失败/未完成业务仍按知识库重建，不逐条回放任务。

原 OBS 对象和原知识库在发布期间未删除，所以文件不需要恢复。回退验收完成前，
禁止删除 `.7` 数据库备份、保留的 postrelease 数据库或旧 K8s 清单。

## 9. 发布完成条件

只有以下全部成立才可关闭变更：自动 platform/final 均 PASS；全部业务 smoke 和 owner
验收完成；Ingress 恢复；24 小时内无异常重启、DB 连接/共享内存错误、模型 admission
错误或新增失败文档；cutoff、数据库备份、digest、容量 before/after 和 tracker 已存档。
