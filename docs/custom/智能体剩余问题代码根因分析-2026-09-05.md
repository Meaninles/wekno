## 结论与证据边界

剩余问题并非一个“上下文太长”就能解释。已定位的实现问题分布在资料分块、候选生成、重排、历史组装、引用投影和 SDK 交付等多个环节。最先应处理的是**证据结构与预算传递**，否则提高模型能力也无法恢复被截掉的适用对象。

| 问题 | 实验证实的实现原因 | 对当前现象的解释范围 |
|---|---|---|
| 安全培训把管理人员 32 学时套到新员工 | token 预算只要为正，受保护表格行就可能按子块的 384 字符硬切；后半行没有对象和培训类别 | 原始 Word 和实际出错的 chunk 21/22 已逐字复现；不是资料自身矛盾 |
| 配了 auto，分块仍缺少结构上下文 | `buildParentChildConfigs` 未传递 `Strategy`，父、子配置都变成空值，实际选 legacy | 调用真实函数验证 auto、heading、heuristic 都丢失；与行硬切是两个问题 |
| 报销流程搜到很多界面，直接 QA 却漏了 | 初段先取小候选池，重排看不到正确 QA；多模态界面文本和直接 QA 共用排序预算 | 当前预算下 39 个候选无该 QA；只在测试请求中扩大预算后，QA 进入重排第 3 位 |
| 长资料相关内容被低估 | generic 重排适配器硬编码 `truncate_prompt_tokens=511` | 同一证据置于长段尾部时几乎得不到分；4096 的控制请求恢复明显相关性 |
| 引用测试通过，实际仍无可点击引用 | 当前 SDK 流式路径与旧引用规范化函数分叉；旧函数仅被测试调用 | 规范 `<src>` 有引用，已知 `（S1）` 别名在当前流路径中为 0；不代表所有无引用都由此引起 |
| SDK 输出工具语法碎片却标记完成 | 解析后的 text 被 `native_result` 接受；成功 `end_turn` 被当成交付依据 | 回环协议实验复现该接受行为；旧 MySQL 样本的碎片最早出现在模型还是网关，尚缺原始出口记录 |
| 文档仍慢 | 模型多次读模板、修改自带 PPT 渲染器、重复写规格、审核与注册，工作被切成很多模型往返 | 最新成功 PPT 普通工具总计约 2.27 秒，VLM 约 21.79 秒，任务约 148.63 秒；不能归为 Office 转换一直很慢 |

验证不以关键词、引用数量、completed 或工具 `success` 判断答案通过。问答内容、工具参数/返回、来源原文和缺失条件均人工检查。组件诊断日志中的 PASS 仅表示观察程序执行完成。

## 1. 知识库：从原文到回答逐段定位

### 1.1 适用对象是在分块阶段丢失的

制度类测试库仍为原配置；父子块开启，`strategy=auto`，父块 4096、子块 384，嵌入模型配置上限 8192 token。业务文档数量不写入版本化报告。

下载脱敏制度样本，用当前开发 DocReader 的 builtin `Docx2Parser` 重新解析。原文转换后的同一 Markdown 行同时含有培训适用对象及学时要求；解析阶段尚未丢失这种关联。

真正的切断发生于 [splitter.go:289](<WORKSPACE_ROOT>/internal/infrastructure/chunker/splitter.go:289)：`TokenLimit > 0` 时将 `maxUnitSize` 直接设成 `chunkSize`。这把“嵌入模型的硬上限”误当成“每个语义单元都不得超过目标子块大小”。即使一行只有 626 字符、远未达到模型上限，也会在约 384 字符处被切断。

| 同一解析文本、同一父子块参数 | 出现 32 学时的块 | 适用对象 | 与旧索引关系 |
|---|---:|---|---|
| 仅诊断：token_limit=0 | 626 字符 | 保留 | 管理人员类别与数值仍在同一行 |
| 仅诊断：token_limit=8192 | 253 字符 | 丢失 | 现有 chunk 21/22 均逐字复现 |

另用普通三列表格，将对象放在行首、结果放在行尾，中间说明分别为 200、500、900 字符：200 字符两种设置都保持关联；500/900 字符在启用预算后，结果块均失去行首对象。这是通用结构缺陷，不依赖安全培训的题目和词语。

不能以关闭预算作为修复。正确方向是区分目标块大小与模型硬上限；确需拆长行时保留表头、行键、合并单元格继承关系和续行身份，不能只留下无对象的后半段。修复后也需要重建受影响资料的索引，单改查询端不能还原已丢失的语义关联。本次没有重建索引。

原文重放与存量文本块有 33 个精确匹配；本次解析未执行图像衍生任务，不把它称为全部索引的逐项重建。

### 1.2 配置选择在调用层被丢掉

[knowledge_process.go:408](<WORKSPACE_ROOT>/internal/application/service/knowledge_process.go:408) 构造父子配置时没有拷贝 `base.Strategy`；[strategy.go:206](<WORKSPACE_ROOT>/internal/infrastructure/chunker/strategy.go:206) 又把空值解释为 legacy。实际服务路径调用了这两个函数。

一次性镜像中直接调用真实函数，得到：

| 配置值 | base | parent | child | 实际策略 |
|---|---|---|---|---|
| auto | auto | 空 | 空 | legacy |
| heading | heading | 空 | 空 | legacy |
| heuristic | heuristic | 空 | 空 | legacy |

因此前端预览所选策略与父子块入库路径可能不同。只改 splitter 内部规则不够，必须让预览、普通入库、父子块、物理分片使用同一个配置解析入口，消除重复构造造成的字段遗漏。

### 1.3 直接 QA 在重排之前已丢失

沿用实际工具生成的三个报销流程查询，阈值保持向量 0.5、关键词 0.3，重排模型和 511 token 参数保持不变：

- 当前候选预算 10：合并后 39 个候选，直接回答“制单人与经办人不一致”的 QA 块没有进入候选池。
- 测试请求候选预算 50：合并后 136 个候选，正确 QA 块进入重排第 3，分数约 0.791；前两项仍是操作界面。
- 实际代码在 [knowledgebase_search.go:152](<WORKSPACE_ROOT>/internal/application/service/knowledgebase_search.go:152) 设置内部召回量，随后在 [同文件:266](<WORKSPACE_ROOT>/internal/application/service/knowledgebase_search.go:266) 再按 MatchCount 截断，外层工具才重排。预算同时影响这两个阶段，不能把控制实验解释为仅改变最后一次数组截取。

四个新库采用同一通用干预，没有为单题调整查询、提示词或模型：

| 知识库与原问题 | 候选数 10→50 | 人工核对排名结果 | 本次重排请求耗时 |
|---|---:|---|---:|
| 运维：制单人不同于经办人 | 39→136 | 找回直接 QA，但界面说明仍占前位 | 0.292→0.914 秒 |
| 移动应用：网络异常现象 | 17→96 | 原有正确问题记录仍第 1，无关网络检测说明增多 | 0.188→0.707 秒 |
| 操作指引：利润分配明细与必填 | 19→86 | 补入同一单据的相关 OCR 块；主操作说明仍在 | 0.176→0.552 秒 |
| 制度资料：审批流程 | 15→74 | 正确条文仍第 1，扩大池带入更多其他制度审批内容 | 0.205→0.375 秒 |

这些是一次请求耗时，不是 p95，也不是四题问答准确率。操作指引的必填信息确实来自图片，不能统一排除截图/OCR。更合理的是将原文、OCR、图像描述归属到同一证据单元，再用独立的召回候选预算和终段证据预算控制速度与覆盖。

### 1.4 重排先获得长文本，随后被硬截断

[remote_api.go:77](<WORKSPACE_ROOT>/internal/models/rerank/remote_api.go:77) 固定发送 511 token。与此同时，[knowledge_search.go:1410](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:1410) 将命中文本、图片描述、OCR 和生成问题拼入 passage。上层认为丰富了证据，下层却可能看不到后部内容。

使用当前真实重排服务，查询和证据句不变，只将证据放到相同无关背景的开头/末尾：

| 参数 | 证据在开头 | 证据在末尾 | 纯背景 |
|---|---:|---:|---:|
| 511 | 0.988465 | 0.000017 | 0.000017 |
| 4096 | 0.979951 | 0.877648 | 0.000637 |

已确认位置敏感来自该预算下可见内容的损失。不能据此断言所有低分都由截断造成。应以实际重排模型能力解析预算，采用保留出处的语义单元；避免上游无限拼接、下游静默截断。

### 1.5 多查询最终又被压成一个排序目标

[knowledge_search.go:292](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:292) 将多个查询用空格拼接，所有候选共用一个全局 TopK。原本用于覆盖不同问题的查询，在终段失去了独立的覆盖信息。

对第 10 轮“一般培训与安全培训区别”的同一候选批次重排：合并查询前五为一般培训 4 条、安全培训 1 条；单独使用安全培训查询时，前五全部来自安全规定。说明两类证据本来都在池里，合并排序会改变覆盖分配。此实验没有证明“固定每库取几条”是正确策略；查询应保留语义关联与覆盖信息，再由模型决定哪些证据足以回答比较问题。

### 1.6 引用缺失、错引、回答错误不能合并判断

当前 SDK 生产路径是 `Service.Run → answerStream.push → FilterAnswerCitations`，见 [service.go:335](<WORKSPACE_ROOT>/internal/custom/modules/generalagent/service.go:335)、[answer_stream.go:37](<WORKSPACE_ROOT>/internal/custom/modules/generalagent/answer_stream.go:37)。旧的 `emitSidecarProductionCandidate` 调用了 `RepairAnswerCitations`，但检索调用位置后确认：它现在只被测试调用。

通用校准记录实验直接调用生产使用的流对象：

| 输入 | 当前流的引用数 | 旧辅助路径引用数 |
|---|---:|---:|
| 正确正文 + 标准 `<src id="S1" />` | 1 | 1 |
| 正确正文 + 已知 `（S1）` | 0 | 1 |
| 与证据完全一致的正文，但无 handle | 0 | 1 |
| 与证据相反的正文 + 有效 S1 | 1 | 1 |
| 未知 S99 | 0 | 0 |

这说明两件事：旧辅助函数通过不能代表当前流式行为；有效来源 ID 也不证明相邻结论得到支持。当前流测试只用了 `refs=nil`，没有覆盖有证据时的完整生产行为。

最终版制度第 10 轮没有平台 handle，只写业务章条；其 0 引用现象符合当前只过滤、不补绑定的路径。不能将它说成“已存在的标准 handle 被前端丢掉”。也不能简单恢复庞大词法补引用模块：应统一原生和 SDK 的证据/引用表示及最终投影，测试真实入口；模型负责将主张与证据对应，程序负责真实出处与引用完整性。

错写条号另有上下文缺口：命中的退改签块从“（七）”开始，未携带所属第四条；用户技能又要求章条说明。可点击来源正确，不代表模型补写的“第三条/第四章”正确。段落、条款、表格行的所属结构应来自解析结果，不让模型从 chunk 序号猜。

### 1.7 有些错误发生在模型已经拿到正确证据之后

最终版制度第 15 轮的 S5 明确写出一项带条件的补助审批要求。该轮 `thinking` 也复述了这条条件，随后却把“包干、不需凭证”推成“不需要额外批准”，最终正文出现同样矛盾。

此例不能归因于未召回、证据被截掉或用户条件丢失。代码能改进证据结构、减少相互冲突的指令和旧答案干扰，但不能据此保证模型不再推断错误。需要保持相同配置，逐轮人工复核事实、适用对象、条件和引用；不再加一条差旅专用规则，也不把词法一致或引用存在当作通过。

## 2. 上下文：选取策略已共享，投递结构仍不统一

`BuildHistory` 共享了用户消息的选取和回读身份，但原生路径的 [agent_history.go:129](<WORKSPACE_ROOT>/internal/application/service/agent_history.go:129) 仍把每轮旧工具调用重建成 assistant/tool 消息。许多工具结果只是“旧检索省略”，却仍占用完整消息位置；旧 `read_conversation` 结果还可能再带入用户原文。SDK 则将历史放入一个 XML 文本块。两套运行时仍有不同的上下文表达。

冻结快速问答第 15 轮真实最终生成输入；当前请求、检索证据、系统提示和模型参数相同，只改变以前轮次的消息：

| 历史方式 | 消息数 | 模型报告的输入 token | 本次耗时 |
|---|---:|---:|---:|
| 当前实现 | 32 | 16,819 | 8.432 秒 |
| 去掉旧工具过程，保留旧答案 | 18 | 15,243 | 9.131 秒 |
| 只保留旧用户消息 | 13 | 13,111 | 8.590 秒 |

三份正文均人工读完，当前行程与批准条件基本保留；未出现可以归因于删除历史的稳定提速。原始模式这次也未复现之前的无条件补助表述，因此不能说删除助手历史已经修好准确性。

另做了培训比较的三个探索性重放：删除历史的两组分别空答、只说要继续检索，不能把 3.5 秒记成提速。该捕获来自可调用工具的迭代，未携带原来的工具 schema，重放不完整，不据此推断线上因果。

最终版通用第 15 轮还携带约 14,147 字符的近十轮助手答案，而近期用户原话只有 381 字符。说明预算仍按轮数控制，助手长答案可能占主体。通用方向应是同一个会话上下文构造器、当前执行过程完整保留、旧工具过程按需回读、用户原文/产物版本作为稳定来源。不能一刀切删掉助手消息，用户可能要求续写、翻译或修改上一份内容。

## 3. SDK 与工具协议：应用接受行为已复现，上游出处仍需记录

真实 MySQL 失败样本只执行了 `db_catalog`、`db_schema`，未执行 `db_query`，最终正文却包含 DSML 工具片段。当前 [final_delivery.py:341](<WORKSPACE_ROOT>/custom/services/general-agent/app/final_delivery.py:341) 接受成功 SDK `end_turn` 的普通文本 fallback；JSON Schema 校验只能检查已经解析成工具调用的参数，无法触及混在 text 里的调用意图。

用实际已安装 SDK/runner 接入容器回环协议服务：

- 返回包含工具碎片的 text + end_turn：没有执行对应工具，仍成功交付 `native_result`，复现应用接受链路。
- 返回标准 `tool_use` + 工具结果 + 最终 text：实际执行 Bash 的固定打印操作，正常得到结果。
- 普通无标记正文：收到流片段后一直等到 Result 才交付。
- 相同正文带当前私有标记：能够在 Result 之前交付；标记本身和尾部保留窗口也增加等待。
- SDK 默认还发起独立标题生成请求。只在探针中使用官方 CLI `--name` 后标题请求从 1 变为 0；本次总时长 2.499→2.554 秒，没有证据支持固定端到端提速。

原始 MySQL 样本没有保存每次模型出口和 SDK 入口的原始协议事件，因此**尚不能确定碎片由基础模型、兼容网关还是 SDK 转换最先产生**。现有 Langfuse 只记录 SDK prompt_layout/累计用量及平台工具过程，无法补出这段缺失证据。

下一步应统一模型适配器的 typed tool/text/reasoning/finish 事件与调用关联，优先使用实际模型支持的协议；把 SDK 的自动标题等非任务调用与平台功能去重。不要增加 DSML 关键词拦截，也不要再增加私有最终答案标记、失败补写模型回合来掩盖协议不一致。

## 4. 文档、数据及其他智能体

### 文档：主要时间不在文件读写和 Office 转换

重新逐项检查最新 Word 两轮及成功 PPT 的所有工具参数/返回：

| 任务 | 应用耗时 | 工具时长相加 | 可确认的流程成本 |
|---|---:|---:|---|
| Word 新建 | 45.645 秒 | 0.551 秒 | 模板读取、生成、检查、审核、注册分别等待模型决策；累计输入 163,249 token |
| Word 日期续改 | 51.453 秒 | 0.688 秒 | 再读模板、读文件、修改、检查；实际审核了两次；累计输入 198,776 token |
| PPTX+PDF | 148.320 秒 | 24.060 秒 | 其中 VLM 21.789 秒；其余工具 2.271 秒；累计输入 547,474 token |

工具时长相加不是关键路径精确分解，剩余时间也不能全写成模型计算。它已经足以排除“最新 Word 的主要耗时是 docx 保存”或“成功 PPT 的大部分时间是 LibreOffice 转换”。

[runner.py:2155](<WORKSPACE_ROOT>/custom/services/general-agent/app/runner.py:2155) 对文档智能体统一准备自带 PPT JSON 规格和渲染器；系统约定要求从该规格开始，能力不够时还让模型修改渲染器。真实 PPT 在首次渲染前读了 5 个文件、修改渲染器 2 次、写同一规格 3 次。这个额外中间层使内容任务变成了部分渲染器开发任务。

应精简强制规格/模板前置流程，允许模型表达完整内容和版式；将通用运行、转换、渲染预览、产物注册做成稳定的公共能力，减少重复模型往返。原文件/版本句柄及按 hash 审核应保留。两轮 Word 的原文件恢复仍有效，不能因速度未改善而撤掉文件完整性修复。

### 数据与表格：可信执行信息仍交给模型重复编造

数据查询的完整流式批量物化已经解决此前的 50,000 行截断和逐行插入；最新 MySQL 工具自身只有毫秒级，不应继续归因为数据源连接不可用。未解析调用属于上一节的协议链路。

表格 [data_analysis.go:422](<WORKSPACE_ROOT>/internal/agent/tools/data_analysis.go:422) 强制图表查询携带 LLM 编写的 `source_mapping`。最新四行图表中，SQL 仅约一百余字符，参数 JSON 1,652 字符，其中 source_mapping 1,261 字符。模型填了不存在的 `model_train_summary.csv!A2/M2` 等四个坐标，四个引用全部未匹配；工具仍返回 success，图表 validation 为 pass，来源 validation 却为 warning。

图表数值正确与来源映射正确被分成两套互不约束的合同；机械 pass 容易被误当作整体正确。文件、sheet、cell/row 的稳定身份应由解析/执行层提供；模型表达业务解释和必要的派生关系，不重复猜系统已知的坐标。额外解释“训练样本规模导致迭代次数变化”仍没有证据，不能用图表数值正确替代语义验收。

## 5. 建议的整体修复顺序

1. **先统一证据结构和预算。** 修复父子块配置传递；区分目标块与模型硬上限；保留条款层级、表格行对象和多模态所属关系。统一预览/入库调用，再对受影响资料做可核对的索引重建。
2. **再统一检索与引用链路。** 分开候选池和最终证据预算，按真实模型能力约束重排输入，保留多查询覆盖信息。原生与 SDK 共用一份证据及引用表示，删除无生产调用的旧规范化路径，验证真实流式入口。
3. **统一运行时上下文和协议。** 当前工具过程完整保留，旧过程按需回读；保留用户原文与确切产物版本。平台和 SDK 的标题、会话管理、最终答案边界由明确的一方负责，减少应用私有协议与跨模型兼容转换。
4. **精简任务执行流程。** 去掉强制自改渲染器等中间层，用稳定通用能力完成文件运行/转换/预览；执行层提供数据和文件来源身份，减少模型填写可由系统确定的重复元数据。

这些改动都应针对共享机制，不使用差旅、培训、订单或某个文档的专用提示词。下一轮验收应重新跑四库自然问题和制度库至少 15 轮连续对话，并检查每轮实际工具参数、全部证据、回答条件及引用；文档检查真实下载字节和页面，数据库与表格检查执行真值与来源映射。

不能承诺结构修复后所有模型推断错误自动消失。已拿到正确证据仍误推条件的案例必须保留，继续用完整人工审阅确认，而不是追加题目规则或把拒答、空答记成高精度。
