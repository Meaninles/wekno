## 一、本轮补充验证改变了哪些判断

本轮新增 11 轮完整应用任务：混合检索两组各 3 轮、Wiki 问答 2 轮、MySQL 2 轮、复杂 Word 转 PDF 1 轮；另有 6 次冻结最终生成对照、6 次工具返回对照，以及使用真实服务/工具代码的隔离组件实验。此前 60 轮完整对话和任务回归仍作为基线。**本轮补充测试不是新一轮完整的 15 轮上下文回归。**

全部使用本地账号对应的测试环境和本地数据。四个重点知识库当前为：公司制度 598 份、爱茅台（企业微信私有部署）6 份、报账系统运维问答知识库 11 份、茅台报账系统操作指引 19 份。四库索引未改动。

### 1. 知识库替换：新文件解析失败时，旧文件确实可能已被删除

这不是笼统的“模型误用工具”。[工具描述](C:/weknora-agent-eval-loop/internal/custom/modules/kbmanager/tools.go:85)、默认管理提示和 [ReplaceDocument](C:/weknora-agent-eval-loop/internal/custom/modules/kbmanager/service.go:291) 都要求：新文件刚写入后，立即调用独立删除工具，不等待解析。后台 [monitor](C:/weknora-agent-eval-loop/internal/custom/modules/kbmanager/service.go:559) 在新文件解析失败时只记录失败，不恢复旧文件。

使用真实管理服务和隔离内存依赖，给新文件相同的解析失败结果：

| 唯一变化 | 替换操作最终状态 | 旧文件 | 新文件 |
|---|---|---|---|
| 按当前约定立即删除旧文件 | failed | 已不存在 | 存在，但解析失败 |
| 对照：保留旧文件等待解析结果 | failed | 仍存在 | 存在，但解析失败 |

这证明当前两步工作流缺少替换的失败原子性。实验没有删除用户资料。修改方案必须包含管理操作的生命周期，不能只改问答链路。

### 2. Wiki 修改：工具会丢失目标知识库身份

[wiki_replace_text.go:71](C:/weknora-agent-eval-loop/internal/agent/tools/wiki_replace_text.go:71) 固定选择 `kbIDs[0]`。输入只有 slug、旧文本、新文本等，没有本次读取所对应的知识库/页面版本。读工具可以返回多个库，写工具却丢掉这个区分。

真实工具的隔离实验先指定目标为 B 库：

| 页面分布 | 实际执行结果 |
|---|---|
| 页面只在 B 库 | 工具去 A 库查找，报不存在，B 未修改 |
| A、B 都有相同 slug 和被替换文本 | 工具返回成功，实际修改 A，B 未修改 |

同类首库选择还出现在 write、rename、delete、flag_issue、read_issue。update_issue 则只检查范围非空后按 issue ID 调用服务，也应纳入同一目标解析合同复核；本轮没有据此断言已发生跨范围修改。

**已有页面版本 CAS 应保留。** [wiki_page.go:107](C:/weknora-agent-eval-loop/internal/application/service/wiki_page.go:107) 会拒绝过期版本，不能把这个问题误写成“底层完全没有并发控制”。缺口在读取结果到工具写入参数之间的身份和版本传递。

### 3. 混合检索：有两个问题，只补模板不能解决漏读 Wiki

隔离知识库有真实 Wiki 页面：培训预算尚未确认、培训日期 11 月 9 日、地点和联系人明确，另有投影仪归还地点。已没有对应文档块。

第一组三轮分别问预算、时间地点联系人、投影仪归还地点，都只调用 `knowledge_search + grep_chunks`，随后说没有资料。工具注册日志确认 Wiki 搜索/阅读工具存在，知识库 Wiki 能力启用，并非 Wiki 工具被过滤。

发现测试智能体通过 API 创建时只传了预设 `system_prompt_id`，正文为空。后端 [CreateAgentEngine](C:/weknora-agent-eval-loop/internal/application/service/agent_service.go:192) 不按这个 ID 解析正文，[默认提示选择](C:/weknora-agent-eval-loop/internal/agent/prompts.go:329) 则按有无知识库选择普通 RAG；前端编辑器另有一套模板回填逻辑。这是 API 与 UI 的配置解析不一致，**不能把原测试配置当成完整的 UI 混合预设**。

第二组创建新测试智能体，原样填入已有混合模板，其他配置、问题、知识库不变。实际系统提示长度发生变化，但三轮仍漏读 Wiki。因而“只把模板补上就修好”的方案已被否定。

继续读取实际工具返回，发现 [knowledge_search.go:1015](C:/weknora-agent-eval-loop/internal/agent/tools/knowledge_search.go:1015) 在零命中时生成 `CRITICAL - Next Steps`，指示没开联网就回答知识库没有相关信息。这把一次文档检索的结果扩成了全局搜索结论，并与混合模板中继续查 Wiki 的约定冲突。

用真实上下文构造器、当前全部 8 个工具定义、持久化的首轮工具调用/返回做下一步选择对照；唯一干预是删除零命中返回中的流程指令，保留零命中事实，不添加“必须查 Wiki”的新提示：

| 重复 | 原工具返回 | 去掉流程指令 |
|---|---|---|
| 1 | 继续 wiki_search | 继续 wiki_search |
| 2 | 继续 wiki_search | 继续 wiki_search |
| 3 | 直接回答没有资料 | 继续 wiki_search |

这是**阶段对照**，不是原请求的逐字节回放；持久化 grep 返回已经压缩。它确认了干预在该实验中能改变一次提前终止行为，不能声称这一处独自解释了全部端到端失败。

独立的内置 Wiki 问答使用相同资料和相同请求模型，两轮都完成搜索、读页和正确引用，分别约 5.52、4.74 秒。说明页面确实能被搜索、阅读和引用。混合链路需要统一能力范围、检索结果合同和配置解析，不能靠强化某一道题的提示词。

### 4. Wiki 目录：旧介绍与实时目录被合成互相冲突的内容

新 Wiki 问答实际读到的 index 中，存储的介绍写着已移除培训安排，但实时目录仍列出培训页面；页面本身确实存在。原始 index API 返回证实介绍来自存储，[renderIndexOverviewForAgent](C:/weknora-agent-eval-loop/internal/agent/tools/wiki_tools.go:28) 再把它与实时目录拼接。

本轮两个回答选择了真实业务页面，没被这段介绍误导；这仍是实际存在的数据表示问题。目录的成员关系、数量和删除状态应由实时索引负责，不能同时由一段模型生成的旧介绍负责。目录也不能作为某个业务事实的证据。

### 5. 强制关闭最终思考：有准确性代价，开启也有耗时代价

[finalize.go:126](C:/weknora-agent-eval-loop/internal/agent/finalize.go:126) 将最终生成的 `Thinking` 固定为 false，没有沿用有效模型/智能体配置。对冻结的真实第 15 轮最终生成输入保持系统提示、当前请求、历史、证据及采样参数不变，只切换通用 thinking 参数，交错执行三组。

| 重复 | 关闭思考：耗时与人工判断 | 开启思考：耗时与人工判断 |
|---|---|---|
| 1 | 8.69 秒；正文说明了无住宿票据时的批准条件，但汇总又写“无额外条件”，内部矛盾 | 13.78 秒；保留行程、金额、审批主体和条件 |
| 2 | 8.63 秒；保留条件，部分汇总表述仍需结合限定段阅读 | 16.12 秒；保留条件，明确假设情形与已确定事实 |
| 3 | 5.33 秒；只输出准备作答的过程文字，没有真正交付最终回答 | 11.47 秒；保留批准条件及假设边界 |

六份输出均已人工读完，均是正常 stop，不是输出 token 截断。第三次关闭思考的短耗时不能计成有效提速。网关在两种模板下报告的输入 token 也不同（16,819 与 14,227），所以只能说输入消息内容固定，不能说服务端 token 序列完全相同。

方案应恢复模型能力配置的完整传递，再按真实任务对照选取能力档位。不能直接将“全局开思考”当成速度和精度都已解决；本组也不足以给出总体准确率。

### 6. 文档：主要延迟仍在多次模型往返，审核没有验证所声称的内容

将此前同一份原始《安全生产教育培训管理规定.docx》通过应用上传并转换为 PDF：

| 项目 | 本轮观测 |
|---|---|
| 总耗时 | 77.831 秒 |
| LibreOffice 转换工具 | 3.115 秒 |
| 所有记录工具时长相加 | 5.625 秒，含两个存在重叠的原文件准备进度项；不是关键路径时间 |
| 除原文件准备/汇总注册外的工具时长相加 | 5.480 秒 |
| SDK 累计 input_tokens | 570,308，多次请求累计值，不是单次上下文长度 |
| 产物 | 25 页 PDF、6,100,736 字节，两幅流程图 |
| 过程错误 | 3 次工作目录相关 Bash 失败；1 次审核缺少必填 issues 后重新调用 |

下载产物并查看全部 25 页。七章、二十五条正文和附件表格、两幅流程图均可见；第 24 页是附件 3 流程图，第 25 页只有该流程的文字标题与页码。重新用同一环境直接渲染原 DOCX，25 页逐页像素与交付 PDF 相同。因此**没有证据指向智能体额外修改了原文件版式**；也不能把同一 LibreOffice 渲染当作独立的 Word 原生排版真值。这里只确认产物有标题单独分页的现象，需要审核识别并如实说明。

真实任务没有执行页面栅格化、读取页面图片或视觉检查，却提交 `passed=true`、`issues=[]`，声明无裁切、版式一致；最后还把原文“七章、二十五条”说成“第一至第二十五章”。[review_artifacts](C:/weknora-agent-eval-loop/custom/services/general-agent/app/runner.py:1120) 验证文件 hash，然后接受模型填写的通过状态；它本身不验证视觉检查已经发生。

结论是：原文件恢复仍有效，转换内容没有在本轮被证明丢失；但**模型多次决策开销、工作目录操作错误、没有实际页面证据的审核通过、最终说明失实**必须都进入方案。不能再把下载成功等同于文档任务整体通过。

### 7. 数据分析：本地测试源已可用，旧 SDK 故障没有被证明修复

Docker 内 MySQL 与 PostgreSQL 测试源已启动。MySQL 原问题新增两次完整应用测试，约 25.62、26.52 秒；均实际执行 SQL，得到 10 笔订单、折前 4,294.80、实付 3,936.80、最大订单 90003，与本地执行真值一致。工具自身是毫秒级。不能再用“旧数据源连接失败”解释这两次测试。

旧样本中的 DSML 片段没有复现。本轮没有改业务代码，因此两次成功**不能作为旧故障已修复的证据**。之前真实 SDK 回环实验已证明应用会接受“普通 text 内含工具语法 + end_turn”，但基础模型、网关、SDK 中谁最早生成旧样本的片段仍缺原始协议记录。

曾尝试给独立测试模型配置透明捕获代理，应用对私网地址的 SSRF 校验拒绝了注册；没有修改白名单或绕过校验，也没有取得这段缺失记录。后续修复应在已授权模型适配器内记录脱敏协议事件，不依赖放宽网络边界。

## 三、实施方案：统一职责，同时删除重复路径

按项目二开规范扩展现有模块，不为每个现象新建一个修复层，也不保留两套兼容实现。数据库、存储、配置变化使用开发环境的一次性迁移与重建；切换时保留旧文件/索引直到新版本准备好，是操作原子性要求，不是维护旧实现。

### A. 把原始资料转成可追溯、不会丢对象的证据单元

1. **统一分块配置解析。** 普通入库、父子块、物理分片及前端预览调用同一个解析入口。Strategy、目标块大小、重叠、模型 token 上限都来自一份有效配置；禁止子路径自行重构一小部分字段。
2. **区分两个预算。** 目标块大小控制聚合，模型输入硬上限控制不可再扩张的边界。完整段落/表格行未触及硬上限时，不因为超过目标值就切断；超长单元按结构拆，不能关闭 token 保护。
3. **结构跟随内容。** 解析输出带稳定 block ID、章节路径、条款位置、表格 ID/表头/行键、图片及 OCR 所属关系。续行重复必要的表头和行键，并标注续段；合并单元格继承信息由解析层提供。
4. **查询证据与展示来源共用这些字段。** 不从 chunk 序号猜业务条号。PDF 没有可靠条款定位时显示真实页码/段落，不生成不存在的章节。
5. **重建受影响索引。** 先用代表性 Word、长表、OCR 文档核对“原文→解析→父子块→向量/关键词→引用位置”，再重建四库受影响资料。新 generation 完成并检查数量、失败项、检索结果后再切换，后台衍生任务与相应 generation 对齐。只修改查询端不能修复存量断裂块。

落点：[knowledge_process.go](C:/weknora-agent-eval-loop/internal/application/service/knowledge_process.go:408)、[splitter.go](C:/weknora-agent-eval-loop/internal/infrastructure/chunker/splitter.go:289) 保留小范围配置/调用修正；复杂结构与预算策略放入现有二开模块的共同入口，避免预览/任务队列另写一份。

### B. 统一 RAG、Wiki、FAQ 与多模态检索的结果合同

1. **拆开候选和最终证据预算。** 单查询/单检索通道候选预算、融合重排预算、最终上下文预算分别配置；移除内外层共用 MatchCount 导致的早截断。四库对照表明直接全局 TopK=50 会增噪并增加耗时，不能作为正式修复。
2. **保留查询归属。** 候选保留命中的 query ID、通道、文档和证据单元身份；按同一对象去重，保留不同子问题的覆盖信息后再选最终证据。统一策略处理比较/综合问题，不给培训、差旅或某个库硬写配额。
3. **按模型能力构造重排输入。** 删除 511 的魔数。重排适配器显式提供可用输入长度，优先提交完整语义单元；过长时按结构窗口评分再归并到原证据。OCR、描述和生成问题不再无限拼到一段末尾；不把 4096 的单次实验值冒充所有模型的最优值。
4. **来源可见范围与返回结果准确对应。** 统一返回 `searched_surfaces / scope / status / results / truncated / errors / evidence_refs`。零命中只能说明这次查过的范围无命中。删除工具输出内的 `CRITICAL Next Steps`、联网开关决定最终答案等工作流指令。
5. **让模型选择下一步，程序保证事实合同。** 工具描述说明功能、参数和返回限制；不在返回数据中指挥模型拒答或强迫每轮多路查询。模型可选择 Wiki 或原文；两者支持不同结论或存在差异时，返回出处/时间/版本，不能用固定词语把一个来源的条件套到另一个来源。
6. **目录只负责导航。** Wiki 的成员、数量、分页从当前索引构建；旧介绍与导航分开，不能让旧介绍声称实时删除结果。目录/摘要导航不发放业务主张证据句柄，真正读页/读原文后才绑定相应证据。
7. **控制耗时。** 批量 embedding、同批候选合并重排、独立读请求有界并发；缓存键包含租户、权限范围、知识 generation、查询、模型及预算。先测各阶段，避免用缓存旧答案掩盖召回失败。

落点：扩展现有 `internal/custom/modules/chatretrieval` 的共享服务，原生 [knowledge_search.go](C:/weknora-agent-eval-loop/internal/agent/tools/knowledge_search.go:292)、快速问答和 SDK 工具只负责接入；[knowledgebase_search.go](C:/weknora-agent-eval-loop/internal/application/service/knowledgebase_search.go:152) 与重排适配器明确预算归属。不是再给三条运行路径分别加补丁。

### C. 一份会话上下文、一份证据集合、一套终态事件

1. **在现有 conversationmemory 上完成统一，而非重建记忆系统。** 由平台一次构造当前用户原文、必要的历史原文、相关助手成品、可回读历史句柄、当前证据及产物版本。原生和 SDK 只负责协议序列化，不自行选择事实、追加另一套摘要或重新解释历史。
2. **按 token 预算取历史，保留可追溯原文。** 当前轮工具调用与结果保持完整协议配对；旧工具过程归档为可回读事件，不重建一串“结果省略”占位调用。旧助手长答案按需要读取，续写/翻译/修改上一产物时仍可取得确切版本，不能一刀切全部删除。
3. **证据允许跨轮按版本复用。** 删除“所有外部问题每轮必须重新搜索”的硬约束。复用的是有来源、hash/generation 且当前权限仍有效的证据快照；先批量确认版本/权限，资料变更或新问题超出覆盖时再查。旧助手说法和旧 S 编号不自动成为新证据。
4. **压缩平台提示职责。** 删除重复的任务重述、同一事实/模态规则在多个模板与 post-tool 区块的叠加。保留一次明确的用户任务、证据与权限边界，交给模型理解；不继续追加差旅审批、训练指标或生命周期词语的专用规则。
5. **统一模型能力设置。** 构建有效配置时确定请求模型、协议、thinking/effort、token 上限及支持的采样参数；native loop、finalizer、SDK 路径都使用同一结果。移除 finalizer 的固定 false。SDK 不支持的 temperature 等参数在配置层明确呈现，不能静默假装生效。
6. **协议事件有唯一所有者。** 应用统一 tool call ID、typed tool/text/reasoning、结束原因、执行错误与交付事件。平台拥有跨轮历史和标题；保留现有 SDK persistence 关闭设置，消除 SDK 的重复自动标题调用。删除私有最终答案分隔符及多处不同的尾部猜测/补写路径，使用适配器提供的通道和 finish 事件。
7. **运行适配器按真实协议能力选择。** 普通模型工具调用优先走其原生协议；SDK 保留为需要其能力的适配器，不把所有模型都强行经由 Claude 兼容转换。迁移前对同模型、同上下文、同工具做完整任务 A/B，确认权限、文件、流式、取消和错误语义均保持；不按模型名称猜能力，不静默降级到不支持工具的通道。
8. **引用只保留一个生产实现。** 扩展现有 sourcerefs，让 native、SDK、流式答案、持久消息、Web/移动端共享同一证据集合和引用投影。仅对已存在来源 ID 做结构解析，不按词法相似度补来源。缺少绑定就如实暴露，不能拿“本轮调用过搜索”替整段正文配引用。删除只有旧测试调用的引用修复/交付辅助路径，测试转向真实入口。
9. **终态不等于语义验收。** 协议 stop 仅表示模型结束；工具执行成功、文件字节完整、来源可定位、回答是否有依据分别记录。不能用正则找 DSML、句号数量或内部完成标签来替代对答案的判断，也不能让空答/过程文字成为成功提速样本。

落点：`internal/custom/modules/{conversationmemory,sourcerefs,generalagent,toolcontract}` 与 `custom/services/general-agent/app` 的协议适配。精简 [agent_history.go](C:/weknora-agent-eval-loop/internal/application/service/agent_history.go:129)、finalize/answer_stream 的重复组装，原生引擎只保留调用点和协议循环。

### D. 服务端统一有效配置与工具定义

1. **模板解析移到同一个服务端入口。** 类型/预设 ID、用户显式覆盖、绑定资源和模型能力在运行前解析成有效配置；前端读取这份结果进行展示。用户显式正文优先，模板 ID 明确指定时由服务端解析；未知 ID 给配置错误，不能静默变成另一个类型。删除前端作为唯一模板正文补齐者的职责。
2. **工具 schema 只有一个源。** 同一参数类型生成 native、SDK/MCP schema，调用前执行相同校验；必填字段对应真正的业务前提。无需填写的空 issues、平台已知的 run/file/source 身份由系统提供，不再让模型重复猜。
3. **错误只解释本次错误。** 返回字段路径、期望类型、可用句柄和实际状态，不用大段重试/工具切换指令。只允许无损的协议级处理，移除用大量字符串修复猜测参数含义的行为。
4. **技能按声明的范围提供。** 原生与 SDK 使用同一技能目录、选择与加载机制；技能正文按需读取。显式用户选择的技能仍被尊重，已有「制度助手」不为测试而关闭。固定库名/五段格式若是该技能自身配置，就明确其适用范围，不能作为所有任务的全局系统指令。
5. **能力和语义不混在描述里。** 数据源、文件版本、可读写库范围由结构化资源提供；模型理解用户意图。工具描述保留用途与限制，不承载整套流程状态机。

落点：扩展现有 generalagent/skillhub/toolcontract 的配置构造，注册于 `internal/custom/bootstrap`；原生 agent service 和前端 editor 保留必要调用。避免再增加一套客户端默认值、一套 native 默认值、一套 SDK 默认值。

### E. 把文档替换和 Wiki 写入交给明确的操作事务

1. **替换是一项持久操作。** 用户确认的旧文档身份/版本和新文件句柄绑定在同一个 operation 中：接收→解析/建立必要索引→发布新 generation→清理旧版本。模型只发起替换、查看结果，不再负责精确时机的 add 后 delete。
2. **失败保留旧可用版本。** 新文件不可解析、必需索引失败、进程重启或用户取消均不能提前删除旧文件。使用现有 documentqueue、generation、写栅栏和操作表完成恢复/幂等，不再建立每个 operation 一个独立轮询状态机。清理失败显示清理待完成，不能误报替换整体失败或触发再次新增。
3. **区分接受、可检索、衍生完成、完全清理。** 不为等待可选 Wiki/图谱任务阻塞首次确认；也不把新文件刚入库说成替换已完成。必要索引范围来自知识库有效能力配置，不能固定只等一种索引。
4. **Wiki 读写共享目标句柄。** 读页返回租户/知识库、page ID、slug、版本；修改、替换文本、重命名、删除、问题标记/更新都经过同一个目标解析器。新建页面显式确定唯一目标库；禁止写入 `kbIDs[0]`。版本冲突返回冲突及当前身份，不自动覆盖更新后的内容。
5. **目录和引用随同一变更版本更新。** 业务页面、目录成员关系、来源关系和后台清理使用当前 generation；用户编辑页面和文档衍生页面的身份明确。沿用已有 CAS，不重复实现另一套并发控制。

落点：改造现有 `internal/custom/modules/kbmanager`，复用已有任务生命周期设施；Wiki 工具适配到共用目标解析/写入服务。删除“立即另调 delete”的提示、工具描述和 monitor 中以新文件解析完成代表替换完成的旧语义。

### F. 精简文档、数据、表格任务的执行链

1. **保留原文件与版本能力。** 原始附件、已生成产物以稳定句柄、hash、版本进入工作区；后续小改使用上一版真实字节，继续保留已修好的格式/内容完整性。
2. **把稳定操作做成公共能力。** 文件清单、转换、代码执行、页面渲染、元数据读取、产物登记由工具确定性处理。执行接口明确 `cwd` 并返回实际工作目录与文件句柄，减少猜相对路径导致的失败；不通过给 Bash 命令拼隐藏前后缀解决。
3. **删除强制自改 PPT 渲染器流程。** 模型负责内容与版式，可使用现有文档库和通用执行环境；平台负责稳定渲染/转换/预览。公共渲染器的能力缺口由代码维护，不能在每次生成任务中让模型临时开发渲染器。模板作为用户格式要求/参考提供，不强制所有格式每轮全文重读。
4. **审核绑定真实检查证据。** 渲染产生页面/区域及检查记录，绑定产物 hash；模型或配置的视觉能力读取这些页面后反馈具体问题。支持批量页面、按 hash 缓存、续改只复核受影响页；数值/正文/媒体差异也由工具提供。删除仅凭 `passed=true` 和长篇自述就解锁的审核合同。
5. **检查状态准确表达。** 文件可打开、文本/图片存在、视觉检查覆盖范围是不同结论。未查看的页面不能宣称没有裁切；同一转换器的重放不能冒充独立排版真值。真实内容/版式验收保留人工阅读，不把页面数量或关键词匹配当通过规则。
6. **合并无必要的模型往返。** 工具自己计算路径、文件类型、hash、大小、检查摘要及登记元数据；模型不必单独调用一次去确认每个可计算字段。修改文件后使旧审核记录失效；不因流程合并复用旧版本审核。
7. **数据来源由执行层生成。** CSV/XLSX 解析时提供文件、sheet、物理行/单元格身份；SQL 结果提供输入来源、查询、列、行集及派生关系。删除强制模型编写物理 source_mapping 的要求；复杂聚合能证明到数据集/查询级就如实记录，不虚构逐格映射。
8. **计算、图表、解释分别核对。** 保留已修好的全量批量物化和完整性标记。图表使用实际结果数据；source warning 不能被 chart pass 掩盖。业务解释由模型根据证据生成，训练样本量与收敛速度等因果结论必须有相应证据，不能通过增加此场景专用禁语解决。

落点：从过大的 `runner.py` 中提取上下文、通用执行、产物检查/登记职责，入口保持薄；扩展现有 artifactstore 与 dbanalytics，接入原生和 SDK。不要为 Word、PPT、PDF、数据分析分别复制工作区和来源管理。

### G. 补齐可诊断性，明确尚未确诊问题的后续动作

1. 统一 run/request/model-call/tool-call 的关联，记录实际模型与协议、配置 hash、模型参数、消息与工具 token、首个协议事件、首个答案字符、工具起止及最终交付时间。模型生成、队列等待、网络、工具执行和页面视觉检查分别计时；资料入库另拆解析、OCR、结构提取、嵌入与衍生任务耗时，不能把整段耗时笼统归给 DocReader 或模型。
2. SDK 协议问题记录三个边界：模型服务返回→兼容适配→SDK 事件，保留脱敏 typed 事件和关联 ID。原始测试内容只进入本地私有材料，不记录 API key/Authorization，也不改生产采集策略。
3. 若原生模型出口已把工具调用写成普通 text，按该模型的真实工具协议/能力配置处理；若出口为 typed call 而中途丢失，修改对应适配器。不能未取得这两类证据就升级/替换 SDK，并宣称故障根因已解决。
4. 正确证据下仍答错、简单指令仍未遵循，先保持相同用户请求与证据做通用上下文/能力对照。若能力配置不能改善到要求，明确模型能力限制，比较可用模型；不加题目提示、不返回固定答案、不靠拒答降低错误样本数量。

## 六、回归与对比如何验收

### 1. 先约束实验方法

- 基线固定为已提交版本；修复组使用相同用户输入、附件字节、模型、技能、知识库快照及权限。索引修复对比使用同源资料的不同 generation，明确区分资料相同与索引不同。
- 检索预算、重排长度、上下文、thinking、协议适配分别做单变量对照，然后做整合端到端；不给某道题补条件、关键词或答案。失败样本、空答、超时和不完整回放全部保留。
- 自动化只负责采集、结构完整性、文件字节和执行事实。问答是否正确、引用是否支持、是否遗漏条件、是否捏造推断，逐轮人工确认。
- 单点耗时不当成 p95；同场景冷/热缓存分开交错重复，先报告各次与中位数。样本足够时再报告分位数。耗时改善必须与交付质量同时成立。

### 2. 制度库连续多轮：每条主要问答路径至少 15 轮

快速问答、智能推理、通用智能体各跑独立连续 15 轮，真实使用 598 份制度资料。保留原有失败问题，再加入未用于调整代码的新问题/自然追问。序列需覆盖：

1. 由自然问题定位原始制度及具体条件；
2. 补充对象、角色、地点等用户事实；
3. 追问相同条款与引用；
4. 修改此前字段；
5. 提出条件性/假设性问题；
6. 合并多条制度依据；
7. 切换到另一类制度；
8. 比较不同适用对象的培训要求；
9. 读取长表/跨块条文；
10. 一般培训与安全培训等跨文档比较；
11. 引用上一答并要求简化或改写；
12. 再次更正此前事实；
13. 回到前一主题检查指代与证据；
14. 在隔离副本更新来源，验证版本失效后重查；
15. 汇总当前已确定与条件性结论，检查各条引用。

这些是覆盖维度，不是强制回答模板或固定断言规则。每轮阅读用户输入、实际发送历史、全部工具 schema/参数/结果、候选及最终证据、完整回答和点击后的来源。新场景的追问根据实际回答自然产生，不只按测试者预期走固定成功路径。

### 3. 四库与其他任务的新增场景

| 范围 | 至少覆盖的新增变化 | 人工核查重点 |
|---|---|---|
| 公司制度 | 新员工/管理人员、一般/安全培训、不同审批角色、例外条件、长表行、跨条款 | 对象、数字、前提、例外、条号与原文位置不能串用 |
| 运维问答 | 口语/同义描述、直接 QA 与界面说明竞争、跨产品相似词、无答案问题 | 直接 QA 是否进入候选；额外流程说明有无依据 |
| 爱茅台 | 故障表现相近但处理不同、版本/网络环境、连续排查追问 | 不把“相近记录”说成同一根因；保留适用边界 |
| 操作指引 | 截图中的字段/必填信息、图文互补、跨页步骤 | 不丢 OCR 证据，不把画面描述自动当业务规则 |
| Wiki/混合 | Wiki 独有、原文独有、来源版本差异、同名不同库、目录更新 | 范围、来源角色和覆盖正确；不能未查另一能力就断言全库无资料 |
| 文档 | 小改原件、多页表格、竖横混排、图片/标题、Word→PDF、PPT→PDF | 下载字节、完整内容、页面视觉、引用/来源、变化范围；不虚报审核 |
| 数据/表格 | 50,001 行边界、状态编码/空值/金额口径、多表聚合、跨 sheet、图表 | 完整物化、真实 SQL、聚合语义、来源定位；数值对不代表解释对 |
| 管理/修改 | 新解析失败、清理失败、重试/重启、并发改页、A/B 同 slug | 精确目标、版本、可用性、幂等、用户可见状态 |

### 4. 通过、未通过及未确诊分开记录

每个场景的审阅记录包含：实际回答是否解决请求、条件/边界是否正确、来源原文与引用是否一致、是否有不必要的工具或恢复回合、错误在哪一层、耗时分布、是否有未检查的文件页或协议段。机械检查通过不能覆盖人工发现的问题。

最终必须提供“已改善、有代价、未改善、未确诊”四类结果及原始证据。旧 SDK 片段首发层、正确证据下的模型推断错误和复杂排版能力都不能在没有证据时直接关闭。

## 八、实施中追加：输入框直接上传的大文件与图片

用户于 2026-09-06 明确追加：在原 A–G 全部目标保留的基础上，手动上传文件及图片每个至少支持 128 MiB，必须验证实际处理能力，不能只调整大小校验。
