## 1. 数据分析既慢又错：执行器先截断，再计算，并反复逐行搬运整表

当前 `db_query` 的流程是：

`读取源表前 N 行 → 在 DuckDB 临时表逐行重建 → 执行用户 SQL → 按返回行数判断 truncated`

源数据库执行的是 `SELECT * FROM 表 LIMIT max_scan_rows`。用户 SQL 中的过滤、聚合、排序，都在截断之后才执行。“聚合只返回一行”因此不表示它计算了全表。

本地 PostgreSQL 边界表有 **50,001 行**，最后一行 `score=1,000,000`。原生 SQL 结果是 `COUNT=50,001、MAX=1,000,000`；智能体两次 `db_query` 返回 **50,000、50,000**，工具成功，`truncated=false`，最终回答明确称其为全量结果。总耗时 125.84 秒，两个查询分别 42.46、40.40 秒。

这条因果链已经确定：**源表先被裁掉一行，模型收到错误且被标成完整的统计结果。** 修改回答提示无法让模型算出未进入执行器的数据。

随后调用原始 `materializeTable` 和相同 Go DuckDB 驱动，仅将网络读取换成固定内存数据，隔离源库和模型影响：

| 相同输入与 SQL | 物化耗时 | 聚合耗时 | COUNT / MAX |
|---|---:|---:|---|
| 50,000 行，现有逐行 ExecContext | 34.246 秒 | 1.10 毫秒 | 50,000 / 50,000 |
| 50,000 行，保留逐行调用，只加事务 | 29.416 秒 | 0.51 毫秒 | 同上 |
| 50,000 行，通用每批 500 行、一个事务 | 0.742 秒 | 0.65 毫秒 | 同上 |
| 相同批量机制，输入完整 50,001 行 | 0.914 秒 | 0.91 毫秒 | **50,001 / 1,000,000** |

批量版本在该组件上约快 **46 倍**。仅加事务改善有限，主要成本是每次查询都重建整表，并对每行单独执行插入；不是 COUNT/MAX 本身慢。这里没有把组件的 46 倍外推成整个智能体的提速倍数。

整体改进应减少搬运：明确只读查询的执行引擎，能在源库完成的计算在源库完成；确需统一分析引擎的场景使用流式/批量导入，按数据版本复用。输入完整性与输出展示上限分开表达。**把 50,000 改成更大的常数不算解决。**

## 2. 上下文差：用户事实被程序删除，来源编号不稳定

**用户事实依赖助手是否完成。** SDK 历史构建器仅保留同时存在用户、助手且 `assistant.IsCompleted=true` 的问答对。保持用户文本完全不变，只将对应助手完成标志设为 false，用户更新同时从最近历史和账本中消失；恢复 true 后，事实恢复。因此中断、超时、工具失败后继续对话，可能连用户已经提交的纠正信息也丢失。模型没有收到这条信息。

**来源 ID 随窗口变化。** 历史读取有界，但来源编号从“这次读到的第一条”重新计数。实验配置最近 5 轮、底层读取 114 条消息；窗口前移一轮，同一条持久化事实由 `user_turn_057` 变为 `user_turn_056`。代码注释称稳定，实际只在当前窗口内稳定。

**账本按位置截断，不是语义压缩。** 48 轮长历史中，第 21 轮末尾的字段既不在最近 5 轮，又被账本逐条长度上限裁掉，最终整个模型上下文都找不到它。只将相同字段移到同一条消息开头，它就重新出现；事实内容没变，结果取决于位置。

目前还有三份历史组装：SDK、原生 Agent、聊天流水线。前两者按助手完成状态筛选，聊天流水线按问答文本非空筛选。同一历史在不同智能体中可能得到不同上下文。最近用户文本同时出现在历史和账本中，重复输入却仍无法保证较早长消息的完整性。

**整体改进：合并一个会话上下文构建器，以持久化 message ID 表示来源，用户消息独立于助手执行状态保留。** 最近消息保持原生角色，旧内容按统一预算压缩，并能通过稳定来源回读原文。删除重复编号、重复账本和多处重新判定历史有效性的逻辑，而不是继续增加语义规则。

依据：[SDK 历史](C:/weknora-agent-eval-loop/internal/custom/modules/generalagent/service.go:927)、[原生历史](C:/weknora-agent-eval-loop/internal/application/service/agent_history.go:67)、[聊天历史](C:/weknora-agent-eval-loop/internal/application/service/chat_pipeline/common.go:225)、[账本](C:/weknora-agent-eval-loop/internal/custom/modules/conversationmemory/policy.go:123)、[窗口/中断实验](C:/weknora-agent-eval-loop/.local-data/agent-audit-20260905/root-cause/component-tests.log)、[长消息位置实验](C:/weknora-agent-eval-loop/.local-data/agent-audit-20260905/root-cause-history/component-tests.log)。

## 3. 文档续改失真：没有恢复原文件；质检也不能保证拦截

每轮 SDK 创建新的 run 目录和 session ID，结束后删除目录。平台保存了 artifact，但历史构建不将其恢复为下一轮输入；`originalInputFileSpecs` 只处理当前上传和当前选中的知识文件。

同一段历史、同一份 Word、原封不动的“只改日期，其余保持不变”请求，对照如下：

| 对照 | 模型实际操作 | OOXML 字节比较 | 总耗时 |
|---|---|---|---:|
| A：现有历史路径 | 查找旧文件，未取得原文件；调用 Document() 重建 | document.xml 和 styles.xml 都变化，并非只改日期 | 38.549 秒 |
| B：仅补回原文件 | 读取现有 Word、检查 runs，然后修改原 run 文本 | 整个包只有 document.xml 变化，且恰好只有指定日期被替换 | 36.943 秒 |

A 最终声称“排版维持原样”，实际文件不支持该说法。B 没有增加提示或编辑规则，编辑方式由同一个模型自行选择。**当前跨轮原文件状态断裂，是这个保真失败的原因。** 这组实验没有显示显著提速：恢复文件解决保真基础，不自动解决过多模型轮次。

另一个独立实验直接调用现有 ArtifactStore：先对文件返回审核失败，一个字节都不修改，再调用注册前检查，仍然放行。第一次失败把全局 `allow_post_repair_artifacts` 设为 true，`ensure_reviewed` 此后直接返回，既不确认修复，也不限定为那份文件。这证明“审核没拦住失败文件”，不能把它说成样式漂移的制造原因。A/B 中则是模型自评通过，但没有原文件可比较。

SDK 实际操作还显示 Bash 可写出 run 目录：A 写入 `/root/`，B 使用 `/tmp/`。本轮生成的这些文件已按哈希核对清理。“新建 run 目录”本身不等于文件隔离，不应靠全局文件搜索恢复会话资源。

**整体改进：同一份会话资源清单管理原文件、工作版本和已交付版本；续改自动恢复具体版本，交付检查绑定字节哈希。** 内容/视觉审核和格式完整性检查各保留明确职责，删除审核失败后整体放行及重复审核状态。无需让用户每轮重新上传，也无需增加“保持格式”的提示。

## 4. 工具错误：描述、schema、执行器不是同一份合同

MySQL 实测里，模型读取 db_catalog 后连续两次 db_query，被 `call db_schema first` 拦截；调用 db_schema 后查询正常。这两次失败不是连接或 SQL 语法错误，而是执行器的前置状态检查。db_schema 描述要求先调用它，但 db_query 自身只要求用 catalog/schema 返回的表名，没有声明这一硬性前提。组件实验确认，改变 `schemaReasoning` 状态就决定是否放行，尚未进入 SQL 计算。

对当前 get_document_info 直接测试：

| 输入 | ValidateParams | 实际执行 |
|---|---|---|
| 空对象 | 放行 | 缺少 ID 数组 |
| 空 knowledge_ids 数组 | 放行 | 缺少非空 ID 数组 |
| knowledge_ids 中放数字 | 放行 | 无法转换为字符串 |
| 截断、无效的 JSON | 放行 | JSON 解析失败 |

第一类原因是 schema 未表达“至少一种非空 ID 数组”；第二类是校验器不递归检查数组元素，并在 JSON 解析失败时返回无错误。都是稳定可复现的实现缺口，不能依靠模型重试弥补。也不能由此把所有历史工具错误都归结为描述问题。

**整体改进：参数类型、schema 和输入校验共用一个定义，错误使用统一类型。** 保留权限、只读 SQL、类型和资源范围检查；删除用“模型是否读过 schema”模拟业务理解的状态机，把元数据作为可获取输入，而不是隐含执行前提。

依据：[数据库工具描述](C:/weknora-agent-eval-loop/internal/custom/modules/dbanalytics/tools.go:33)、[状态前提](C:/weknora-agent-eval-loop/internal/custom/modules/dbanalytics/service.go:1488)、[文档信息 schema](C:/weknora-agent-eval-loop/internal/agent/tools/get_document_info.go:47)、[校验器](C:/weknora-agent-eval-loop/internal/agent/tools/param_validate.go:27)、[组件实验](C:/weknora-agent-eval-loop/.local-data/agent-audit-20260905/root-cause/component-tests.log)。

## 5. 召回不稳定：证据过早合并，服务故障被表示成空结果

**去重由到达顺序决定。** 同一个 chunk 的候选分数为 0.1、0.9，仅交换输入顺序：低分先到就保留 0.1，高分先到就保留 0.9。第一遍 seen 已丢掉后到候选，后面的“保留最高分”循环无法挽回。

同一父块下、正文不同的两个子块也只保留先到者。实验交换顺序后，留下的证据正文改变。上游真实 SearchResult 使用子块正文并携带 ParentChunkID，所以不是不可能出现的输入。**并发返回顺序会决定哪些证据还有机会进入 rerank，模型无法选择已删除的片段。** 这不等于已经证明 Atlas 每次错答都由它造成；那个现场样本未做逐步候选消融。

**阈值不是实际最低过滤分数。** 配置阈值 0.5，输入重排分数 0.09、0.08、0.07、0.06，仍保留前三个，因为固定 recall floor=3。已证明低分候选越过阈值，未证明所有低分候选都无用；应统一弱候选保留与证据充足的含义。

**检索故障变成成功的无证据结果。** 对真实 concurrentSearchByTargets 注入连接失败，错误只写日志，返回空候选；继续走 formatOutput，得到 Success=true 和 “No relevant content found”，并要求模型告知用户知识库没有相关信息。因果链是：后端不可用 → 空列表 → 成功的无证据结果 → 错误归因。

**整体改进：按真实 chunk 身份聚合最高分，保留不同证据片段，使用一处重排/筛选政策；完整、部分成功和检索失败明确区分。** 删除父块过早去重与错误压成空数组的处理。现有“同 embedding 模型合并检索、查询向量复用”应保留，不应为精简而删掉有效批处理。

依据：[去重](C:/weknora-agent-eval-loop/internal/agent/tools/knowledge_search.go:990)、[上游子块结果](C:/weknora-agent-eval-loop/internal/application/service/knowledgebase_search_results.go:312)、[阈值保底](C:/weknora-agent-eval-loop/internal/agent/tools/knowledge_search.go:931)、[吞没错误](C:/weknora-agent-eval-loop/internal/agent/tools/knowledge_search.go:543)、[顺序/阈值实验](C:/weknora-agent-eval-loop/.local-data/agent-audit-20260905/root-cause/component-tests.log)、[故障注入实验](C:/weknora-agent-eval-loop/.local-data/agent-audit-20260905/root-cause-extra/component-tests.log)。

## 6. SDK 固定开销、重复模型调用与正文等待已测到

使用当前 claude-agent-sdk 0.2.110 和实际 runner，模型端为容器回环地址定时服务：每 0.35 秒一个片段，约 1.75 秒发完。真实模型、外网、检索和文档处理不参与。

| 项目 | 结果 |
|---|---|
| 直接读取同一定时服务 | 首片段约 0.352 秒，总计约 1.753 秒 |
| 保留现有 SDK 会话持久化，两次 | 7.538 / 7.312 秒；正文几乎最后才出现 |
| 只关闭 SDK transcript 持久化，两次 | 4.897 / 4.872 秒；正文仍最后才出现 |
| ResultMessage 到达后，现有模式继续等待 | 约 2.33 / 2.25 秒 |
| 关闭 transcript 后仍等待 | 约 1.42 / 1.43 秒 |
| 每次实际模型 HTTP 请求数 | 两种模式都为 2：会话标题生成 + 主回答 |

关闭持久化只是诊断，不是建议改一个开关上线：它没消除标题调用或末尾等待，现有重试又依赖 SDK resume。应整体明确会话生命周期的管理者。

结果已通过 ResultMessage 到达，但 runner 要等 query() 完整迭代结束才投影正文；Go 桥接又缓存 answer_delta，等整个 sidecar 返回后再发前端。Python 收到 text delta 时也先缓冲。多层处理使支持流式的模型表现成整段等待。额外仪表确认 SubprocessCLITransport.close() 本身在这些样本中几乎立即返回，不能把最后这段时间直接说成这个 close 方法耗时；确定的是结果完成后仍等待查询迭代结束才交付。

数据、表格每轮还先单独调用 SDK 判断是否画图，再启动主任务。真实模型实测这一前置步骤约 5.88～7.26 秒。4 行表格的 schema/计算约 132/13 毫秒，却总计 24.15 秒。快速问答开启 query understanding 时同样先独立调模型；三轮纯对话中为 3.48～4.17 秒，约占总耗时 78%。简单对话路径没有这次前置调用。

**整体改进：统一执行与完成事件处理，减少独立前置分类，明确 SDK/平台的会话所有权，删除重复终结协议和正文缓冲。** 让主模型的结构化工具选择/输出承担相应意图表达，避免先由一个模型判断，再将其变成另一个模型不可改变的指令。不是简单把所有智能体迁到同一个 SDK。

## 7. 冗余上下文与配置失效：已证明机制，不能随意量化精度损失

真实文档 transcript 按 message ID 去重后，A 有 9 轮主模型调用，输入从 **35,503** 到 **39,222 token**；B 有 8 轮，从 **36,179** 到 **40,615 token**。提供方上报 cache read token 均为 0，不能进一步推断其内部绝对没有任何缓存。

代码中的重复来源包括：visible_context 再携带完整 agent.system_prompt，随后被塞入用户消息，而同一 baseline 已用于 SDK system prompt；最近用户文本重复出现在历史和账本；当前请求在可见配置、头部和尾部 replay 重复；工具接口之外又生成文本目录；多个合同重复解释历史、来源和终结输出。文档每轮还准备模板及 PPT 工作文件，局部编辑仍有多次查找、读取、审核和注册的模型往返。

**重复工作已确认，“删掉后精度必然提高多少”尚无证据。** 应先删除同一信息的重复表达，保留一份权威配置、消息和能力目录，对大资源按需读取，再用未参与修改的样本验收。

另有确定的配置问题：runtime_config.temperature 从 0 改为 1，实际 SDK 请求均没有 temperature 字段。该值进入 runtime_summary 文本，未成为采样参数。不能以界面相同 temperature 推断 Go 与 SDK 采样设置一致，也不能把它直接当作文档失真的唯一原因。

## 8. 从四条共享链路精简现有系统

建议围绕现有代码收敛，不增加一套旁路修复引擎。

| 共享链路 | 合并或删除的复杂度 | 保留的职责 | 验收 |
|---|---|---|---|
| 会话上下文与资源 | 三份历史、窗口重编号、重复全文账本、全局找文件 | 持久消息身份、原生角色、旧消息回读、文件版本/句柄 | 中断不丢事实；来源不漂移；续改恢复原件 |
| 模型执行与交付 | 重复前置分类、双重会话管理、多套终结标记与正文缓冲 | 原生工具循环、统一生命周期、一次完成判定、增量引用检查、真实调用记录 | 正文不等待无关收尾；模型调用实际减少；工具结果与交付一致 |
| 检索与证据 | 父块过早去重、先到先留、分数规则叠加、错误变空数组 | 批量混合检索、来源身份、单一重排政策、完整/部分/失败状态 | 到达顺序不影响证据；故障不等于无答案 |
| 数据/文件执行 | 每条 SQL 重搬整表、schema 语义状态门槛、审核失败整体放行、文件重建 | 只读执行器、输入完整性、批量处理、版本化 artifact、字节级检查 | 大表统计正确；批量提速；非目标内容/样式差异为零 |

各智能体主要保留能力范围、领域指令和可访问资源的差异。消息、文件、工具输入和执行结果应共用定义，避免每种类型复制一份“识别—判断—调用—修复—解释最终结果”。先保证输入/状态正确，再减模型往返；不能通过关闭能力、固定很小的 top_k 或扫描上限、删掉必要信息或提前终止制造提速。权限和格式检查属于执行器，业务理解和选择属于模型。

## 9. 各类智能体覆盖与结论边界

| 类型 | 已确认的共享影响或专有原因 | 实测边界 |
|---|---|---|
| 简单对话 | 聊天历史筛选应纳入统一上下文 | 上轮直接回答约 1.02 秒；不应额外增加 SDK/图表预检 |
| 快速问答 | query understanding 串行耗时、重复历史、历史语义不统一 | 已测三轮和明确范围检索；工具版去重实验不等于它的所有步骤 |
| 智能推理 / RAG | 原生历史筛选/编号，知识检索去重、错误传播、工具合同 | 对话、检索和共享组件有实测 |
| 通用 | SDK 生命周期、缓冲、重复上下文、temperature 不落地、文件跨轮状态 | 真实问答和定时模型实测；SDK 是框架，真实问答不是 Claude 模型 |
| 文档处理 | 缺少原文件恢复、审核状态失效、8～9 轮大上下文调用 | Word A/B 与全包比较；复杂 PPT/PDF 视觉质量未全面验收 |
| 表格分析 | 图表前置调用、SDK/终结合同、参数一致性 | 4 行 CSV 计算快；不能自动套用另一 db_query 的 5 万行缺陷 |
| 数据分析 | 提前截断、逐行物化、schema 状态门槛、图表预检 | 本地 MySQL 聚合、PG 边界表有数据库真值 |
| 维基问答 | 原生上下文、工具合同与检索状态应统一 | 目录问答 4.52 秒且正确；未证明当前慢因是 regex 或模型队列 |
| RAG + Wiki | 原生上下文和普通检索缺陷适用；共用来源和失败状态 | 不应复制另一套合并及错误解释规则 |
| 维基修订 | 原生执行/历史共性；页面写入依赖明确版本与权限 | 审阅配置和实现，未为诊断改写用户 Wiki，不宣称修订成功率已验证 |
| 知识库管理 | SDK 生命周期、历史/资源状态；操作完成与解析完成需区分 | 沿用已有后台操作状态，避免模型轮询；未诊断性增删用户知识库 |
| 自定义及旧自动操作 | 按实际 runtime 和工具继承上述原因 | 不按名字另写修复；未实例化常量不算运行中的智能体 |

## 10. 对初步结论的收紧

1. 数据库慢现在有物化对照支持；源库或模型算得慢不适用于该边界样本，加事务也不足以解决。
2. 文档保真有原文件 A/B 和实际操作支持，但没有泛化成所有文档问题都只缺文件。
3. 上下文冗余有具体来源；已确认事实丢失首先发生在程序筛选、编号和截断，不能全部称为大模型被提示干扰。
4. SDK 已分出固定生命周期、标题请求和交付等待；不能凭端到端差异推断全部来自 prompt 或启动进程。关闭 transcript 不是完整修复。
5. 三个 API 的工具 callback 分别指向对应副本，本轮不把跨副本丢失工具状态列为当前根因。
6. DocReader 并发限制、gRPC 长连接分配、模型准入排队、复杂文档衍生长尾尚未完成因果隔离，不列入已确认根因。小文件 core-ready 与 enrichment 时差只说明需要分阶段计时。
7. 之前默认全库的 Atlas 探针不能算显式选库失效，明确范围结果已单列。本轮确认共享组件缺陷，不强行给每个历史错答指定同一原因。

后续实现以四条共享链路为边界：先修状态和输入完整性，再减少重复模型调用与协议层。使用覆盖多个智能体、未参与改动的不同任务验收，同时记录准确性、首个有效正文、总耗时、真实模型调用、工具错误和产物差异。
