**1. 多轮会话目前保存了很多文字，却没有充分保存可继续工作的状态**

这部分同时影响准确率和速度，建议最高优先级处理。

- **已复现：文件续改不保真。** 两份 Word 下载后的 SHA256 与注册信息一致，内容只有目标日期变化，但 OOXML 显示标题从非粗体改为粗体，正文从“仿宋”改为“仿宋_GB2312”，首行缩进从 640 改为 0。模型仍称“其余内容均未改动”。[文件核验](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/artifact-verification.json)、[具体格式差异](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/artifact-document-xml.diff)。
- **代码确认：每轮 SDK 运行都是新工作目录、新配置目录、新 session_id。** 请求结束会清理运行目录。Go 端历史主要保留 user/assistant 文字及附件元信息，没有把上一轮已生成的 artifact 版本、可访问文件句柄、工具工作状态自动还原成下一轮可操作对象。这样“修改刚才文件”容易变成依照旧回答重新生成。[SDK 运行目录](<WORKSPACE_ROOT>/custom/services/general-agent/app/runner.py:5901)、[会话创建](<WORKSPACE_ROOT>/custom/services/general-agent/app/runner.py:6080)、[历史构建](<WORKSPACE_ROOT>/internal/custom/modules/generalagent/service.go:900)。
- **代码确认：用户事实账本与最近历史重复。** `BuildUserSourceLedger` 再放一遍近期用户消息；SDK 运行提示又多次重复当前请求、语义约束和终结协议。首轮仅 46 个字符的测试，Go 传入的系统提示有 16,845 字符，另外渲染的运行提示有 27,068 字符。这是字符数，不是 token 数，也未包含完整工具 schema 开销。[账本](<WORKSPACE_ROOT>/internal/custom/modules/conversationmemory/policy.go:123)、[运行提示](<WORKSPACE_ROOT>/custom/services/general-agent/app/runner.py:3158)、[实测提示长度](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/prompt-full-observations.json)。
- **代码风险：长会话来源编号会随窗口变化。** 历史先按条数截取，再对窗口里的完成问答从 1 编号。窗口滑动后，相同 `user_turn_N` 不再必然指向同一持久消息。`IsCompleted=false` 的问答对整体不进入 SDK 历史，因此上一轮用户给出的有效修正，也可能随被中断的回答一起丢掉。[编号与完整对过滤](<WORKSPACE_ROOT>/internal/custom/modules/generalagent/service.go:963)。这两个边界尚未做长轮次模型实测。
- Go ReAct 还会保留部分工具历史并在阈值触发后做模型摘要；摘要最多 3 次、每次 60 秒的调用可能放大长尾。它是条件触发路径，不能据此断言本轮短对话发生了摘要。[压缩器](<WORKSPACE_ROOT>/internal/agent/memory/consolidator.go:17)。

建议把上下文统一成：稳定的消息 ID、最近原生角色消息、当前任务状态、带来源和版本的证据、artifact 版本与当前文件句柄。用户事实即使对应回答中断也应保留；历史 assistant 可作为“要改写的文本对象”，但不能自动晋升为事实来源。跨轮引用根据内容版本和权限重新绑定句柄，不必对每次改写重新检索全文。文件续改应打开上一版字节并做局部修改，再核验内容和样式差异。

SDK 可以评估持久 client/session 和工作区复用，同时保留租户隔离、生命周期和并发会话锁；不要只增加 history_turns。官方 SDK 文档支持会话恢复，但实际恢复与缓存效果还要在本项目 DeepSeek/Qwen 网关上测量：[SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)、[Python SDK](https://code.claude.com/docs/en/agent-sdk/python)。

**2. 一些“让模型更可靠”的前置步骤，已经成为明显延迟来源**

快速问答在需要问题理解的路径上，先单独调用模型改写和分类，再调用模型回答。表格与数据库分析则先调用 SDK 模型决定是否画图，之后才进入实际分析。本轮 4 行表格中的 6.35 秒图表预判，甚至比直接查表长几个数量级。[问题理解调用](<WORKSPACE_ROOT>/internal/application/service/chat_pipeline/query_understand.go:150)、[图表预判入口](<WORKSPACE_ROOT>/custom/services/general-agent/app/runner.py:6037)。简单对话探针没有该调用，说明不能把所有 quick-answer 类型一概当成同一耗时路径。

建议让主模型在首次决策中同时选择“直接答、检索、分析、是否需要图表”，把可选的结构化意图放在同一次决策里；检索查询本身由模型在确实需要检索时形成。不要再增加一个分类模型来替代现有分类模型。对于已经有明确结构化 UI 选项的约束，由接口传递事实；对于自然语言歧义，由主模型判断。

规则需要分类处理：权限、SQL 只读、文件存在、版本一致性、数值运算、schema 和产物结构校验应由程序保证；任务理解、证据是否足以回答、生成内容及版式策略应交给模型。当前大量约束是重复的语义提示和终结状态协议，不全是关键词规则。继续增加类似“当前任务优先、旧格式过期、逐命题自检”的段落，既增大输入，也可能与历史和专用提示互相冲突。

另一个独立问题是答案缓冲：Go 收到 SDK `answer_delta` 后暂存，等本轮结束、统一做引用校验才发给前端。本轮通用对话 10.82 秒，首个正文约 10.52 秒；文档 37.63 秒，首个正文约 37.12 秒。[缓冲位置](<WORKSPACE_ROOT>/internal/custom/modules/generalagent/service.go:324)。可以在保留引用与落库一致性校验的前提下，对已确定的正文片段逐段验证并输出。这个改进主要降低首个有效答案的等待时间，不能冒充总耗时下降。

**3. 工具错误不只是描述写得不好，存在 schema、执行器和运行配置不一致**

历史中提取到 1,387 条明确记录失败的工具调用，包含 Bash、知识检索、文件读取、artifact、SQL 与参数问题。由于其中混有旧版本和测试，这是排查索引，不是当前失败率。[错误索引](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/history-errors.json)。

当前代码中可以直接确认的契约缺口：

- `get_document_info` 的 schema 不要求任意一个 ID 数组，也没有非空数组条件；执行器却要求 knowledge_ids / knowledge_base_ids / faq_ids 至少一项非空。模型调用 `{}` 可以通过该 schema，但必然在执行时失败。[schema 与执行检查](<WORKSPACE_ROOT>/internal/agent/tools/get_document_info.go:47)。
- `ValidateParams` 只做部分顶层校验；空参数、非法 JSON、非法 schema 会返回 nil，嵌套对象、数组元素、anyOf 等也没有完整覆盖。只修工具提示而不统一校验器，会继续出现“看起来合法、运行时报错”。[验证器](<WORKSPACE_ROOT>/internal/agent/tools/param_validate.go:27)。
- **本次已复现 db_query 调用顺序错误：** MySQL 10 行订单统计中，模型连续两次在 db_schema 之前调用 db_query，被执行器拒绝。工具公开描述和前置门槛分散在不同工具中；应统一公开契约，并让运行时自动满足能够确定的元数据依赖，避免多次模型往返只为取得一个“已读 schema”的状态。保留字段、权限和只读 SQL 校验。[数据分析工具](<WORKSPACE_ROOT>/internal/custom/modules/dbanalytics/tools.go:36)、[实测调用](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/probe-mysql-analysis.json)。
- `query_knowledge_graph` 描述称无图谱配置时会返回普通检索，实际执行遇到未配置图谱会记录错误并跳过该库。需要使公开能力契约与执行结果一致，而不是让模型靠试错发现。[描述](<WORKSPACE_ROOT>/internal/agent/tools/query_knowledge_graph.go:40)、[执行](<WORKSPACE_ROOT>/internal/agent/tools/query_knowledge_graph.go:152)。
- SDK 原生工具、MCP 名称、业务工具别名及不同终结方式并存。历史出现过不存在的 `weknora_final_response`、provider 不支持的 tool_choice/thinking 组合、缺少 Chrome 等运行依赖。这些应分别归为协议、模型能力和工具环境问题。当前工作树已有终结协议修复；本轮成功任务没有复现旧的 final-response 工具错误，不能把它当作未修复缺陷。

建议从同一份类型定义生成模型 schema、服务端校验、文档和真实调用契约测试；完整支持所用 JSON Schema 子集。工具只暴露当前模型和运行环境确实支持的能力。返回结构化错误码、可重试性、缺失字段和候选 ID；对能够唯一解析的运行时 ID 由服务端绑定，避免模型抄 UUID。只对真正缺少的信息让模型修正，避免重复调用同一个无效工具。

还应保留内部可审计的参数和原始结果引用。当前对话持久记录里许多 `args` 为 null、结果只剩“执行完成”，前端精简展示合理，但仅靠会话回放不足以复现工具错误。

**4. 检索已有混合召回和重排，下一步重点应是证据适用范围与检索结果组织**

项目已经有向量/关键词混合检索、RRF、reranker、复合评分、MMR 和去重，不缺少基础检索组件。本轮明确限定单库的检索耗时低于 1 秒；默认全库场景明显更难保持主体准确性。不能仅靠继续加大 top_k 提升回答精度。

代码层面还应处理：

- **去重过早且不保证保留最高分。** 在重排前先按 parent ID 等键保留最先到达的结果，可能丢掉同父段下不同证据；并发召回结果到达顺序又可能不同。后面的“最高分”处理无法恢复已经丢掉的候选。[调用顺序](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:265)、[去重](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:990)。优先按原始片段 ID 去重、保留来源和子问题覆盖，再按 token 预算组织父段及相邻证据。
- **重排阈值存在保底召回。** 当前至少保留前三个有效排序项，即使分数未达到配置阈值。这有召回收益，但在无答案、相近术语不同主体的场景也会增加噪声。应通过固定反例集校准，不能把“有返回”当成“有依据”。[保底策略](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:931)。
- **多查询最后合并为一个重排问题。** 多个子问题直接用空格拼接，整体相关度高的段落可能挤掉只支持其中一项的关键证据。应保留 query→chunk→claim 的覆盖关系，再做一次全局组织，避免每个子问题都开启新一轮模型检索。[重排输入](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:285)。
- **部分检索错误被当成无结果。** 并发分支遇到 HybridSearch 错误只记录日志，最终只返回已有结果；Wiki 搜索遇到数据库错误也直接 continue。模型容易把“没搜成功”解释成“知识库没有”。应区分空结果、部分失败、全部失败；失败不能通过普通答案掩盖。[检索分支](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:543)、[Wiki 分支](<WORKSPACE_ROOT>/internal/agent/tools/wiki_tools.go:682)。
- 已配置 BGE reranker 的测试不应归因于 LLM 重排。但无专用 reranker 的其他配置会走每 15 段一次、顺序调用聊天模型的分支，需要明确配置并在启动时校验，避免无意中进入高延迟路径。[LLM 重排](<WORKSPACE_ROOT>/internal/agent/tools/knowledge_search.go:669)。

建议把显式 KB / 文档 / 标签范围作为硬约束；全库检索保留“适用主体、版本、生效范围、来源段落”元信息，避免将一类制度套到另一类业务对象。摘要和生成问句适合帮助召回，具体数值和要求仍要回到原文。当前已有摘要映射原文引用的处理，应保留并评估，不需要推倒重做。

对缓存，优先缓存可验证的 embedding、重排结果、文档片段和解析结果，键中包含 tenant、权限/范围、文档版本和模型版本。避免直接跨权限或跨文档版本复用最终答案。SDK 提示词前缀也应尽量稳定，但缓存收益必须看实际 provider 的命中指标：[Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

**5. 文档生成的“质量审核”目前不足以保证交付质量**

`review_artifacts` 主要接受同一个生成模型传来的 passed、issues、alignment，登记文件指纹。第一次失败后设置 `allow_post_repair_artifacts=true`，`ensure_reviewed` 会直接放行修复后的文件，不再核验新字节。PPT 另有结构/几何检查，但不能覆盖真实字体、换行和渲染效果。本次 Word 格式漂移也通过了审核。[审核实现](<WORKSPACE_ROOT>/custom/services/general-agent/app/runner.py:1212)、[修复后放行](<WORKSPACE_ROOT>/custom/services/general-agent/app/runner.py:1262)。

建议用格式专用的执行步骤缩短链路：模型决定内容与编辑意图，一次生成结构化操作；Word 做节点级局部编辑，表格用确定性计算，PPT 使用可扩展渲染器。运行时按任务按需准备对应格式的模板和依赖，避免每轮加载全部格式材料。质量门槛用真实文件打开、结构、内容、计算、版本差异和必要的渲染检查；语义与视觉评价用模型判断。修复后至少对新字节重复廉价的确定性核验，不能只沿用旧的“已审核”。

历史中也有 PPT 请求单轮约 179 秒、19 次工具调用的实例，下一轮又约 130 秒、15 次工具调用。这支持减少重复搜索、读取 skill、环境探测和重新生成的方向，但不能据此断言本轮 Word 的慢完全由相同原因造成。复杂 PPT 的版式效果还需要独立样本和渲染验收，尚未给出当前准确率。

**6. 数据库分析已复现输入截断导致错误全局结论，列为 P0**

当前 `db_query` 将涉及的源表读取到 DuckDB 临时表，再执行模型 SQL。`materializeTable` 每次重新建表，并逐行 Exec 插入。源表读取本身带 `LIMIT maxScanRows`，默认上限 50,000；结果的截断标志主要根据输出行数，而不是输入是否完整。[查询执行](<WORKSPACE_ROOT>/internal/custom/modules/dbanalytics/service.go:1323)、[逐行物化](<WORKSPACE_ROOT>/internal/custom/modules/dbanalytics/service.go:1433)、[源表 LIMIT](<WORKSPACE_ROOT>/internal/custom/modules/dbanalytics/connector.go:250)、[默认上限](<WORKSPACE_ROOT>/internal/custom/modules/dbanalytics/types.go:60)。

因此，大表的全局 SUM/MAX、排序、JOIN 可能只在截取部分上计算；输出只有一行也不证明输入完整。这个风险已完成运行验证：在新启动的独立 PostgreSQL 测试库建立 `audit_probe.boundary_rows`，插入 50,001 条合成数据，第 50,001 行设置 score=1,000,000，其他行为 score=id。数据库直接查询确认 count=50,001、max=1,000,000、对应 id=50,001。

智能体两次 db_query 都显示成功，实际返回 count=50,000、max=50,000、id=50,000，`limits` 还标记 `truncated:false`。最终回答明确声称这是“核心结果（全量，非样本）”。这是工具输入完整性缺失造成的真实错误，不能仅通过要求模型“更仔细核验”解决。[独立真值](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/database-oracle.txt)、[智能体答案](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/probe-postgres-scan-boundary.json)、[实际工具 SQL / 返回值 / 截断标志](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/messages-postgres-scan-boundary.json)。

性能也得到验证：两次工具查询分别 42.46、40.40 秒，合计 82.86 秒，占 125.84 秒总耗时约 66%。同一测试表在原生 PostgreSQL 执行 COUNT/MAX 的 `EXPLAIN ANALYZE` 执行时间为 5.56ms，扫描了全部 50,001 行。原生执行时间不包含 API 和网络开销，不能直接当作端到端加速倍数，但结合逐行重新物化的代码，足以把数据搬运/物化列为明确排查重点。[原生查询计划](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/postgres-native-explain.json)。

建议在权限和只读约束内下推过滤与聚合，或使用带版本的全量分析快照；确需搬运时采用批量/Appender/Arrow 等方式和明确的内存预算。结果必须包含 input_complete、扫描行数、源总量或是否触顶，区分输出分页和输入取样。无法完成全量计算时应明确说明，不能报告全局结论。SQL schema 的作用域和生命周期应与数据源/表版本一致，减少同轮或连续轮的重复 catalog→schema→query。

按用户补充要求，已从项目现有 `custom/dbanalytics-test/docker-compose.yml` 启动 MySQL 与 PostgreSQL 夹具。MySQL 保持 `127.0.0.1:13306`，应用原连接直接恢复；PostgreSQL 的原宿主端口 15432 与本地主库冲突，通过忽略目录中的 Compose override 改为 `127.0.0.1:15433`，并在开发环境中建立 `DBAnalytics PostgreSQL 测试库（测试）` 只读连接。两者均通过应用连接检查。旧 `E2E 通用智能体 PG 只读源` 保留，没有修改其账号或权限。新源已追加到数据分析智能体的 `db_data_sources`；仅修改了该配置键。[连接结果](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/datasource-connection-results.json)、[绑定变更](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/data-agent-source-update-result.json)。

MySQL 补测第一轮得到 10 行、金额聚合与最大值；第二轮先按订单聚合支付和退款，再按客户汇总，结果与数据库直接 SQL 一致。具体业务金额、客户姓名、订单号和文件证据仅保存在本地忽略目录，本文不记录。这一组没有复现数值错误，但复现了额外预判、前置调用失败和较多模型往返。[答案与耗时](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/probe-mysql-analysis.json)、[执行 SQL 与结果](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/messages-mysql-analysis.json)、[数据库独立核验](<PRIVATE_EVIDENCE_PATH>/agent-audit-20260905/mysql-oracle.txt)。

**8. 知识入库慢，需要与智能体生成文档慢分开测**

当前已经拆分了解析、衍生、Wiki、维护角色，也有核心就绪与衍生状态、批量索引和检查点。继续优化应建立在这些机制上。

本地测试条目均为 core ready，其中一部分 enrichment 状态为 degraded，包含摘要失败。它们混有历史测试，不能解释为当前生产失败率。较新样本表明，小型 Markdown 从创建到核心可用较快，但衍生阶段可能明显变慢；对这些小文件，后续生成比基础解析更值得检查。详细状态只保存在受保护的本地证据中。

下一步应分开记录上传、队列等待、原文解析、OCR/VLM、切块、embedding、摘要/问句/图谱、Wiki、首次可检索的耗时；按文档版本和能力依赖复用已有结果，失败重试只补缺失阶段。核心 ready 应清楚展示，已启用的衍生能力继续完成或明确报错，不能通过关闭能力、截断内容来假装提速。

两个尚需压测验证的瓶颈：DocReader 的 gRPC worker 默认 4，但 MarkItDown、ODL、PDF render 各有默认 1 的并发限制；三个 DocReader 后面的 HAProxy 使用 TCP round-robin，分配的是长连接，未必均匀分配每个 gRPC 请求。因此不能仅凭容器数量判断实际解析并发。[解析并发配置](<WORKSPACE_ROOT>/docreader/config.py:85)、[DocReader 入口](<WORKSPACE_ROOT>/custom/tests/runtime_profile_e2e/haproxy-docreader.cfg)。还要测模型准入队列与聊天、embedding、rerank、VLM 等共享资源的争用，再调并发。

**建议实施顺序与验收方式**

1. **先修正确性基础：** 数据库输入完整性和全量聚合、artifact 跨轮恢复与局部编辑、用户消息独立持久化、稳定来源 ID、schema/执行器一致性、检索错误分类。验收包括超过扫描上限仍得到真实全表 COUNT/MAX，“只改日期”的未指定内容与样式差异为 0、中断后继续能记住用户修正、长会话来源不漂移。
2. **再减关键路径：** 合并问题/图表意图调用、短任务直接回答、压缩重复提示、按需加载能力、流式输出和 SDK/文件复用。以同模型同输入为基准，分别测首个有效答案、总耗时、模型调用数和 token；无工具通用对话先以总耗时下降至少 30% 为验证目标。目标不代表已经实现。
3. **再优化检索与专用任务：** 多问覆盖、按主体与版本组织证据、去重修正、Wiki 语义召回、SQL 下推/批量物化、格式专用编辑与渲染。不能用固定小 top_k、低轮数或过早截断换取速度。
4. **最后做并发与长尾治理：** 实测模型准入、连接池、解析器并发和文档阶段资源；按 1/4/8 并发及长文档分别看 P50/P95、成功率、峰值内存和取消恢复。当前单请求探针不足以推算并发容量。

建议固定一个独立验收集：多轮修正/中断/指代与文件续改，单问/多问/否定/无答案/同词不同主体的检索，带表格与脚注的文档问答，合并单元格/大表聚合，Word/PPT/PDF/Excel 生成和局部修改，Wiki 回源与修订，知识库增删改状态。历史问题用作回归参考，另留未参与提示修改的语义样本，避免每次只对某几个旧对话加规则。

答案应同时评估事实正确、证据支持、关键项完整、合理拒答和格式效果；速度统计必须把失败、空答案、模型重试、工具重试分开。文件生成成功以实际可下载且内容/格式合格为准，不能只看模型说“已完成”。

本次已完成环境拉起、代码与本地历史分析、功能探针、测试源连接及报告；未实施上述业务优化，也未对大文档压力和复杂 PPT 视觉效果作性能承诺。
