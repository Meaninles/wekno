# 聊天模型会话队列与生产配置

> 适用代码与生产基线：2026-09-13。模型目录、资源与完整发布约束见
> [当前生产实现与部署基线](./当前生产实现与部署基线.md)。

## 1. 目标

聊天队列解决的是“有界接纳、真实并发和用户等待体验”，不是把供应商无法执行的请求
无限堆进 API：

- 两个主交互模型池合计允许 48 个会话同时执行；具体模型名和路由属于受保护生产配置；
- 两个池合计最多等待 52 个会话；
- 平台最多接纳 100 个主要聊天会话，100 包含正在执行的 48；
- 超出个人或模型池上限的请求在创建消息前返回结构化 429；
- 已接受请求在 Redis 共享 FIFO 中等待，通过 SSE 自动晋升，不要求用户重试。

48/52 是按实际模型资源池分别限制，不是一个可以在两个模型间随意借用的全局队列。
后台/衍生模型池可按调度策略承担复杂任务，但不分配主交互等待位。

## 2. 唯一容量来源

会话执行数不由 API 副本数、旧系统设置或前端配置决定。每个实际模型路由绑定唯一
`custom_model_resource_pool`，有效配置由容量控制模块编译：

```text
chat running = max_inflight
background max = max_inflight - interactive_reserve
document_burst <= tenant_burst <= max_inflight
chat waiting = chat_max_waiting
```

Web 与 IM 使用独立会话票据域，避免企业微信占满 Web 等待室；二者的真实 provider
调用仍受同一个 `max_inflight` 保护。`chat.queue.default_max_concurrent` 等旧键不再是
执行真源。

## 3. 当前生产有效值

| 生产模型池（名称受保护） | 已验证能力 | `max_inflight` | `interactive_reserve` | 后台上限 | `chat_max_waiting` | `tenant_burst` | `document_burst` |
|---|---:|---:|---:|---:|---:|---:|---:|
| 主交互池 A | 受保护配置 | 32 | 28 | 4 | 36 | 32 | 2 |
| 主交互池 B | 受保护配置 | 16 | 14 | 2 | 16 | 16 | 2 |
| 后台/衍生池 | 受保护配置 | 32 | 8 | 24 | 0 | 32 | 4 |

两个主交互池的用户会话关系为：

```text
running = 32 + 16 = 48
waiting = 36 + 16 = 52
admitted = 48 + 52 = 100
```

`interactive_reserve` 是防止后台文档任务挤占交互的保护数，不是额外增加的并发。
例如主交互池 A 仍只有 32 个 provider 槽，其中后台最多使用 4；没有交互竞争时，
work-conserving 调度可以利用空闲容量，但不能超过 32。

模型均经受保护生产网关配置验证，不以直连模型节点的
结果作为生产证据。模型显示名与内部部署地址分离，文档不展开实际网关或节点地址。
私有 TLS 需要放宽校验时使用 `insecure` 参数，不降级为 HTTP。

## 4. 限制层级

一次聊天请求依次经过：

1. 个人等待上限：防止单个用户占满所有等待位；
2. 实际模型池等待上限：决定是否仍可接纳；
3. 模型池会话 FIFO：在所有 API 副本间共享顺序与租约；
4. provider 资源池：真正调用模型前再次执行总量、租户、RPM/TPM 准入。

池满和个人满必须返回不同的结构化错误码。拒绝发生在消息写入前，前端要恢复输入框，
不能留下幽灵用户消息或永远“生成中”的助手消息。

## 5. 多副本和故障语义

- Redis 保存共享 FIFO、活动租约和等待者，API Pod 只保存当前 SSE 连接状态。
- 三个 API 副本共同执行一个模型池上限，不能把 32 误解为每 Pod 32。
- 关闭一个 API 副本后，其租约到期或显式释放，等待者由其他副本继续晋升。
- Redis 不可用时 fail closed，聊天返回结构化 503；禁止退化到每 Pod 本地计数。
- 热调低容量不打断在途请求，新请求等待活动数自然下降；热调高容量会立即晋升等待者。
- 取消等待请求必须原子释放个人与模型池名额，新请求无需重启即可进入。

## 6. ReAct 和长会话

会话票据从回答开始持有到最终完成，ReAct、多次工具调用和长输出仍只计一个聊天执行
会话，但其持有时间会更长。provider 的每次真实模型调用仍需资源池准入，因此复杂
ReAct 不能绕过资源池有效配置的底层总并发。

容量验收不能只发短问答，应同时覆盖：

- 普通 RAG、无知识库对话和长输出；
- 多轮 ReAct、工具调用和取消；
- 两个主交互池同时有执行和等待；
- 三 API 副本分流、单副本退出与恢复；
- 个人等待满、池等待满、Redis 故障和恢复。

## 7. 与后台文档并发的匹配

聊天和后台共用实际模型资源池。当前交互保护使后台最多使用：

| 资源池 | 后台最多占用 |
|---|---:|
| 主交互池 A | 4 |
| 主交互池 B | 2 |
| 后台/衍生池 | 24 |

后台优先使用后台/衍生池及各专用 Embedding、Rerank、VLM、ASR 额度，衍生/Wiki 按
`3:1` 权重和 `prefetch_factor=2` 调度。容量等待 30 秒后返回 typed deferral，任务
回到 PostgreSQL 耐久队列；这不是业务失败，不增加 provider attempt 或用户看到的
解析失败次数。

文档链路最多同时接纳 12 个完整工作流，其余知识库和文档可以在 PostgreSQL 排队。
因此 10 个知识库、约 1000 份文档共同解析不会把聊天执行数乘大。

## 8. 管理与变更

管理员在“设置 → 平台 → 容量与调度”修改资源池，并按以下顺序操作：

1. 读取 `/api/v1/custom/capacity-control/effective` 和当前 `policy_version`；
2. 使用 `/validate` 检查单池字段、聊天总量和跨模块冲突；
3. 带 `If-Match` 或版本号保存，避免覆盖他人的并发修改；
   4. 执行 reconciliation，确认生产模型绑定到预期实际路由；
5. 再读 effective、Redis 队列和在线实例，证明运行时已经采用新值；
6. 做小规模真实会话验证，再扩大到目标压力。

修改模型地址或下架模型时必须保留资源池引用完整性。旧音频模型已下架，音频能力统一
使用当前受保护配置中的 ASR 资源池；具体模型和 `max_inflight` 以容量页为准。

## 9. 观测与告警

至少监控：

- 每个模型池 running/waiting、个人等待数、晋升速率和拒绝原因；
- 等待 P50/P95、会话执行 P95、SSE 连接数和 API 内存；
- provider 实际并发、429/5xx、首 token、总耗时和长时间无进度；
- Redis 可用性、租约过期和取消释放；
- 后台 task/provider lease、typed deferral 和真实失败次数。

队列长度只是瞬时负载，不等同于模型故障。若 running 长时间满而 provider 没有实际
请求，应检查资源池绑定、租约和网关；若 provider 正常但 P95 上升，再评估输出长度、
ReAct 步数与交互预留。

## 11. 回滚

- 单池配置错误：恢复该资源池上一版有效配置并重新 reconciliation，不删除模型记录。
- 队列 UI/协议异常但 provider 正常：可以关闭聊天等待功能，让新请求按有界拒绝处理；
  已执行请求保持完成或显式取消。
- Redis 不稳定：保持结构化 503，先恢复 Redis，不启用本地降级。
- 模型网关异常：保持路由和容量绑定，恢复外部 llmgateway；不要临时直连生产模型。
- 数据 schema 或应用版本回滚：按发布手册恢复应用与数据库一致点，不能只回滚前端。
