# 聊天模型会话队列与生产配置

> 适用代码基线：当前工作区；生产环境只读核对日期：2026-07-31。
> 本文描述已经在本地多实例环境实现并通过 API 并发/故障测试的行为，以及基于
> `weknora` 生产 CCE 集群现状计算出的发布配置。本文不是已执行的生产变更记录。

## 1. 结论

聊天限流采用“按实际模型路由共享的会话队列”，不把 API Pod 数量乘进并发：

- 每个实际聊天模型资源池的 `max_inflight` 同时是最大执行会话数；等待会话数独立配置。
- 同一个用户在所有聊天模型资源池中共享一个等待上限，默认 3。
- 等待请求已经被系统接受，使用 SSE 持续返回位置，到位后自动执行。
- 模型池满和个人排队满在消息创建前直接拒绝，不生成幽灵对话。
- 配置由管理员修改后跨 API 实例热生效；增大执行上限会直接放行已有等待请求。
- Redis 是多 API 副本队列的共享事实源。Redis 不可用时聊天准入 fail-closed
  返回结构化 503，但普通健康检查和不依赖 Redis 的基础 API 仍可用。

这套设计有意不增加“全平台所有模型合计上限”“租户聊天会话上限”或“知识库聊天
会话上限”。它解决的是聊天模型被瞬时并发打满和单用户无限占队问题，不把文档、
检索、Agent 和所有 HTTP 请求合成一套难以解释的总闸门。

## 2. 限制层级和边界

| 层级 | 范围 | 当前行为 |
|---|---|---|
| 聊天队列开关 | 全部署 | 默认开启；关闭后新聊天绕过会话队列 |
| 最大执行会话 | 每个实际模型资源池、全集群 | 等于资源池 `max_inflight`，没有第二个聊天并发旋钮 |
| 最大等待会话 | 每个实际模型资源池、全集群 | 代码默认 500；生产建议覆盖为 200 |
| 单用户最大等待 | 用户在全部模型池中的合计 | 默认 3；只计算等待，不计算正在执行 |
| 模型调用准入 | 实际模型路由/租户/文档 | 原有 `modeladmission`；限制单次供应商调用 |
| 文档工作流准入 | 全集群和解析实例 | PostgreSQL 持久队列；与聊天队列相互独立 |

两个容易混淆的概念：

1. “会话并发”从收到聊天请求一直占用到流式回答完成、出错或用户停止。它保护
   用户可感知的完整一次会话。
2. “模型调用并发”只覆盖一次供应商请求。标题生成、对话、Wiki、摘要等都可能
   产生模型调用。后台占用由 `max_inflight - interactive_reserve` 限制，交互请求
   在空闲时可以使用整个资源池，实现工作保持（work-conserving）。

同一模型在多个租户中复制成不同 `models` 行，只要实际路由指纹相同，就进入同一个
资源池和同一队列；API 副本扩容不会把上限放大。不同知识库使用同一模型时也共享
该模型队列。知识库本身没有聊天专属上限。

## 3. 管理员配置

### 3.1 全局设置

| 设置键 | 类型 | 内置默认 | 合法范围 | 生效方式 |
|---|---|---:|---:|---|
| `chat.queue.enabled` | bool | `true` | true/false | 热生效 |
| `chat.queue.default_max_waiting` | int | `500` | 0–100000 | 热生效 |
| `chat.queue.max_waiting_per_user` | int | `3` | 1–1000 | 热生效 |

解析优先级为：

```text
system_settings 数据库值 > 对应环境变量 > 内置默认
```

对应环境变量：

```text
WEKNORA_CHAT_QUEUE_ENABLED
WEKNORA_CHAT_QUEUE_DEFAULT_MAX_WAITING
WEKNORA_CHAT_QUEUE_MAX_WAITING_PER_USER
```

另有部署级安全预算：

```text
WEKNORA_CHAT_QUEUE_MAX_WAIT_SECONDS=3600
WEKNORA_REDIS_NAMESPACE=<每套部署唯一名称>
```

最大等待时长不放进普通管理员 UI，避免把入口代理超时、客户端重连语义和服务端
租约拆开修改。生产 Ingress 的 read/send timeout 已核对为 7200 秒，足以覆盖建议的
3600 秒排队预算和 900 秒模型调用预算。

### 3.2 资源池覆盖

聊天类型资源池的总并发和等待字段为：

```json
{
  "max_inflight": 24,
  "interactive_reserve": 6,
  "chat_max_waiting": 300
}
```

- `max_inflight`：模型调用与聊天执行会话的唯一总并发。
- `interactive_reserve`：限制后台最多占用 `max_inflight - interactive_reserve`。
- `chat_max_waiting`：0–100000；0 表示不接受等待，只允许立即执行。
- 修改继续使用资源池 `policy_version` 和 `If-Match`，并写管理审计。
- 缩小并发不会中断已经执行的会话；只有活动数下降到新上限以下才继续放行。
- 缩小等待数不会踢出已接受的请求，但会拒绝新的超额请求。

## 4. 用户可见状态

| 情况 | HTTP/SSE | 前端显示 | 输入和消息 |
|---|---|---|---|
| 立即执行 | HTTP 200 SSE | 正常回答 | 正常创建 |
| 已接受等待 | HTTP 200，`queue_status=waiting` | 蓝色排队卡；位置变化；到位自动执行 | 已创建，可取消 |
| 到位 | `queue_status=admitted` | 排队卡结束，自动进入回答 | 无需重新提交 |
| 单用户排队满 | HTTP 429，`CHAT_QUEUE_USER_LIMIT` | 橙色个人上限提示 | 恢复输入，不创建消息 |
| 模型池队列满 | HTTP 429，`CHAT_QUEUE_FULL` | 红色系统繁忙提示 | 恢复输入，不创建消息 |
| Redis/控制面不可用 | HTTP 503，`CHAT_QUEUE_UNAVAILABLE` | 服务暂不可用 | 恢复输入，不创建消息 |
| 无可用聊天模型 | HTTP 503，`CHAT_QUEUE_MODEL_UNAVAILABLE` | 模型配置不可用 | 恢复输入，不创建消息 |

桌面和移动端使用同一结构化错误，不依赖中文文案判断类型。排队状态写入现有 Redis
stream，刷新或重新连接后仍可恢复。用户点击排队卡“取消”时调用原有 session stop
接口，服务端幂等移除活动/等待租约并立即释放个人等待名额。

## 5. 多实例和故障语义

Redis key 使用共同 hash tag `{chat-queue}`，保证原子 Lua 脚本涉及的 key 在 Redis
Cluster 中属于同一 slot。主要租约：

| 项目 | 值 |
|---|---:|
| 活动会话租约 | 90 秒 |
| 活动心跳 | 25 秒 |
| 等待租约 | 45 秒 |
| 等待轮询/续租 | 500 毫秒 |
| 资源池热配置缓存 | 每 API 实例、每池 1 秒 |

边界说明：

- 单 API Pod 停止时，入口继续路由到其余 API Pod；新请求继续共享同一个上限。
- 已经绑定到故障 Pod 的 SSE 连接会断开，客户端需要用现有 stream 恢复/重试机制
  处理；不能把一个已经在某进程中执行的 HTTP 请求无损迁移到另一进程。
- 硬故障遗留的等待记录最多在等待租约后清除；活动记录最多在活动租约后清除。
- Redis 全部不可用时不允许每个 API 各自降级为本地队列，否则会把集群上限乘以
  Pod 数；生产多实例必须 fail-closed。
- 单实例、无 Redis 的 Lite 开发模式仍保留进程内 FIFO，语义与 Redis 队列一致。

## 6. 本地验收基线

本地使用与目标生产角色相同的多实例形态：

```text
API 3
parse-worker 2
derivative-worker 2
wiki-worker 2
maintenance 2
DocReader 2 + 入口
Redis / PostgreSQL / MinIO 共享
```

聊天专项 API 测试共 9 组通过：

- 全局继承：执行 1、等待 2、并发发起 6，准确接受 3、系统满拒绝 3。
- 资源池覆盖：执行 2、等待 5、并发发起 10，准确接受 7、系统满拒绝 3。
- 个人限制：执行 1、个人等待 2、并发发起 5，准确接受 3、个人满拒绝 2。
- 取消一个等待会话后，新会话无需重启即可进入空出的个人名额。
- 执行上限从 1 热调到 3 后，已有等待会话自动晋升，观察到活动数大于 1。
- 两个不同实际模型资源池各自保持独立的执行/等待容量。
- 关闭一个 API 副本后，剩余两个副本仍精确执行共享上限；恢复后健康加入。
- Redis 全停时聊天返回结构化 503，基础 API 健康；Redis 恢复后聊天恢复。
- 请求实际分布到多个 API 容器，拒绝会话的消息数保持 0。

此外，24 份 PDF、DOCX、XLSX、CSV、Markdown、纯文本的并发文档矩阵覆盖了双用户、
四知识库、多模型、多衍生任务以及各专用角色单副本/全副本故障恢复。

## 8. 推荐生产拓扑

### 8.1 Go 运行角色

所有角色使用同一不可变 app 镜像，不同 Deployment 只改变运行角色：

| Deployment | 角色 | 副本 | request/副本 | limit/副本 | 放置 |
|---|---|---:|---:|---:|---|
| `weknora-api` | `api` | 3 | 1C / 2Gi | 2C / 4Gi | `.1/.2/.7` 各 1 |
| `weknora-parse-worker` | `parse-worker` | 3 | 1.5C / 3Gi | 4C / 6Gi | `.1/.2/.7` 各 1 |
| `weknora-derivative-worker` | `derivative-worker` | 2 | 0.75C / 1.5Gi | 2C / 3Gi | 三个工作节点跨主机打散 |
| `weknora-wiki-worker` | `wiki-worker` | 2 | 0.75C / 1.5Gi | 2C / 3Gi | 三个工作节点跨主机打散 |
| `weknora-maintenance` | `maintenance` | 2 | 0.25C / 512Mi | 1C / 1Gi | 不同主机，PG advisory leader |
| `weknora-migration` | `migration` Job | 1 次 | 1C / 2Gi | 2C / 4Gi | 发布期间唯一运行 |

首发期按现有节点余量建议使用以下首选落点：

| 角色 | Pod 1 | Pod 2 | Pod 3 |
|---|---|---|---|
| API | `.1` | `.2` | `.7` |
| parse-worker | `.1` | `.2` | `.7` |
| derivative-worker | `.1` | `.7` | — |
| wiki-worker | `.2` | `.7` | — |
| maintenance | `.1` | `.2` | — |
| migration Job | `.7` | — | — |

这里的“落点”应用节点标签、`preferredDuringScheduling`、Pod anti-affinity 和
`topologySpreadConstraints` 表达，不使用不可恢复的 `nodeName` 硬绑定；节点故障时
允许 Pod 在其余 `.1/.2/.7` 工作节点重新调度。按此分配，衍生、Wiki 和维护角色的
额外 CPU request 分别落为 `.1=1C`、`.2=1C`、`.7=1.5C`，避免把新增角色全部压到
已有两个 Agent 和 Web 副本的 `.1/.2`。

公共环境：

```text
CUSTOM_RUNTIME_ENV=production
CUSTOM_RUNTIME_ROLE_ENFORCED=true
AUTO_MIGRATE=false
WEKNORA_REDIS_NAMESPACE=prod-cce-wk-6a9d12b0
```

各 Deployment 分别设置 `WEKNORA_RUNTIME_ROLE`。公网 `app` Service 只选择
`weknora-api`，worker 不进入 Ingress endpoint。

数据库连接池不能继续给每个新 Pod 都配置 8：

| 角色 | max_open/副本 | max_idle/副本 | 集群预算 |
|---|---:|---:|---:|
| API ×3 | 6 | 2 | 18 |
| parse ×3 | 6 | 2 | 18 |
| derivative ×2 | 4 | 1 | 8 |
| wiki ×2 | 4 | 1 | 8 |
| maintenance ×2 | 3 | 1 | 6 |
| migration | 3 | 1 | 发布时 3 |

常态 Go 连接预算为 58，发布迁移时 61，给 LiteLLM、运维和故障连接保留余量；
PostgreSQL 当前 100 连接上限无需因为 Pod 增多就盲目提高。

## 9. 用户量和文档量不会怎样“自动打崩”

### 9.1 聊天

以 DeepSeek 初始值 24/300、个人等待 3 为例：

- 10 个用户同时提交：最多执行 10；个人最多等待 3。
- 100 个用户同时提交：最多执行 24、池内最多等待 300。
- 1000 个用户同时提交：仍最多执行 24、池内最多等待 300；超出者收到 429，
  不会继续创建消息和模型调用。

因此单个模型不会因用户数线性放大执行并发。等待时间近似为：

```text
队列位置 × 一次会话 P95 时长 ÷ 最大执行会话数
```

最大等待设置过大不会增加模型并发，但会增加 API 长连接、Go goroutine、stream
状态和未完成消息数量。生产不建议直接使用合法范围的极端值 100000。

仍需明确：当前没有“所有模型池等待数合计”的全局上限。如果有 5 个活跃模型池，
按上述配置理论上可同时存在约 750 个等待连接。API 3 副本按每副本约 250–500 个
等待 SSE 连接预留 2Gi request，并监控连接数、内存和队列 P95；新增大量模型路由时
要同步核算所有池的等待上限之和。

### 9.2 文档和知识库

文档数量本身不等于并发：

- 100、1000 或 10000 份同时上传仍只有 12 份完整工作流执行，其余在 PostgreSQL
  持久等待；模型子任务再受全局模型池、租户和文档窗口限制。
- 不同知识库共享集群文档容量，没有“每知识库固定 N 个槽”的单独硬上限。
- 某知识库的大批量任务可能影响其他知识库，公平性主要来自队列顺序、租户模型
  准入和每文档窗口，而不是知识库配额。

当前生产 5049 份知识已占约 15GiB 数据库，其中缓存、span、embedding/chunk 是主要
空间。10000 份在同类数据分布下属于可规划扩容范围，但必须有缓存清理、span 保留、
autovacuum、备份和磁盘告警；“一亿份文档”不是当前单 PostgreSQL/单 Neo4j 架构的
容量目标，必须先分区、归档、拆存储和做多集群设计。

租户、知识库和文档的静态数量不会绕过聊天模型队列，但其他入口仍需各自保护：
上传体积、租户存储配额、文档持久队列、数据库连接、检索分页和 API/WAF 速率限制。
聊天队列不是全站 DDoS 或存储容量控制器。

## 10. 发布顺序

1. 保持生产维护状态，完成 PostgreSQL/PVC/配置备份；记录镜像 digest。
2. 对 617 个 finalizing、2409 个 deleting 记录完成原因和恢复/清理对账。
3. 把 `asynq.concurrency` 从持久值 10 改为 4，但在新 parse-worker 滚动完成前
   不开放流量。
4. 运行唯一 `migration` Job；确认资源池、binding、衍生工作表和两个 chat 字段。
5. 检查 41540 条模型 reconciliation 数量、实际路由池数量和重复指纹。
6. 先部署 maintenance、worker、DocReader，确认健康和 advisory leader。
7. 部署 3 个 API，Service 只选择 API；再部署前端和 Agent。
8. 设置全局聊天队列值，再按实际模型池设置覆盖；检查三 API 读取相同 policy。
9. 用 API 依次验证立即执行、蓝色等待、橙色个人满、红色系统满、取消和自动晋升。
10. 执行单 Pod/全角色故障矩阵；Redis 故障时确认聊天 503、基础 API 仍健康。
11. 观察模型 429/5xx、队列位置、SSE 连接、DB 连接、Pod 内存和 P95/P99 后再开放。

现有 Helm Chart 只有一个 `app` Deployment，不能直接表达上述五类 Go 运行角色。
正式发布前必须先增加对应模板/values，并通过 `helm template`、server-side dry-run
和 `kubectl diff`；在模板完成前，本文是部署设计基线，不是可直接 apply 的清单。

## 11. 回滚

- 队列行为异常但 API/数据库正常：先把 `chat.queue.enabled=false`，新请求恢复原
  行为；保留正在执行会话，等待已有 waiter 被放行或取消。
- 单个模型配置错误：只清空该资源池覆盖为 `null`，回到全局值。
- Redis 不稳定：不要开启 API 本地降级；保持结构化 503，先恢复 HA 写入口。
- 需要回滚应用镜像：新表和可空字段可保留；先停止新角色，再恢复旧 Deployment。
- 数据迁移或工作流 schema 不可逆时，按数据库备份点回滚，不能只做
  `kubectl rollout undo`。
