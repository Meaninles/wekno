# 长耗时模型任务有界重试与无丢失部署

本文覆盖图片多模态与 Wiki 两类长耗时模型任务。目标不是把无法识别的输入伪装成
成功，而是同时保证：

1. 可处理任务在模型恢复后继续执行；
2. 单个毒任务不会长期占住整个队列；
3. 达到有限尝试上限后保留明确的失败结果和死信，不静默丢失；
4. app 重启、滚动更新和 Redis 投递重复不会破坏 PostgreSQL 中的持久事实。

## 运行语义

| 场景 | 尝试计数 | 队列行为 | 最终记录 |
|---|---:|---|---|
| 请求到达 VLM/Chat 后超时、5xx、限流 | +1 | 延迟重试并轮转 | 成功，或达到上限后失败/死信 |
| 共享断路器已打开，远端请求未发出 | 不增加 | 按 Retry-After 等待并轮转 | 持久任务保留 |
| Pod 关闭或任务上下文取消 | 不增加 | 由持久计划/恢复器重新投递 | 原 generation 保留 |
| 确定性坏图片或坏 Wiki 输入 | +1 | 不阻塞其他任务 | 达到上限后可审计失败 |

默认总尝试次数均为 10。Wiki 单次模型调用最长 900 秒，批内不再重复三次；
一次失败后交回 PostgreSQL 持久队列。Wiki 选择顺序为 `fail_count`、未尝试优先、
`claimed_at`、`id`，因此旧毒任务不会反复占住 FIFO 头部。多模态图片使用独立
Asynq worker server，不占用通用后台任务线程。

相关参数：

```text
CUSTOM_WORK_RETRY_IMAGE_MAX_ATTEMPTS=10
CUSTOM_WORK_RETRY_WIKI_MAX_ATTEMPTS=10
CUSTOM_WORK_RETRY_WIKI_INLINE_ATTEMPTS=1
CUSTOM_WORK_RETRY_WIKI_CALL_TIMEOUT_SECONDS=900
WEKNORA_LLM_CHAT_TIMEOUT_SECONDS=900
WEKNORA_MULTIMODAL_TASK_CONCURRENCY=2
```

`CUSTOM_WORK_RETRY_WIKI_CALL_TIMEOUT_SECONDS` 不能大于底层
`WEKNORA_LLM_CHAT_TIMEOUT_SECONDS`，否则实际仍会被较小的传输超时截断。

## 更新前保存业务基线

先停止新上传/重建入口，但不要删除 Redis key、Asynq 队列、PostgreSQL pending
行、knowledge 行或对象存储文件。记录发布 SHA、镜像 digest，并完成 PostgreSQL
可恢复备份。然后把以下查询保存到本次变更目录：

```sql
SELECT parse_status, count(*)
FROM knowledges
WHERE deleted_at IS NULL
GROUP BY parse_status
ORDER BY parse_status;

SELECT tenant_id, scope_id AS knowledge_base_id,
       count(*) AS pending,
       min(enqueued_at) AS oldest,
       max(fail_count) AS max_fail_count
FROM task_pending_ops
WHERE task_type = 'wiki:ingest'
  AND scope = 'knowledge_base'
GROUP BY tenant_id, scope_id
ORDER BY pending DESC, tenant_id, scope_id;

SELECT count(*) AS committed_fanout_documents
FROM knowledges
WHERE deleted_at IS NULL
  AND parse_status = 'processing'
  AND processed_at IS NOT NULL
  AND processing_fanout IS NOT NULL;

SELECT task_type, count(*)
FROM task_dead_letters
WHERE task_type IN ('wiki:ingest', 'image:multimodal')
GROUP BY task_type
ORDER BY task_type;
```

这些数不是要求更新期间保持不变；它们用于证明每个更新前的 pending 项在更新后
只能处于“仍 pending、成功完成、明确失败/死信”三类之一，不能凭空消失。

## 更新顺序

本仓库生产环境仍按
[当前版本生产更新部署执行手册](./当前版本生产更新部署执行手册.md)执行。针对本次
变更必须额外满足以下顺序：

1. 保持 PostgreSQL、Redis、对象存储、LiteLLM 和模型端点运行，不执行
   `FLUSHDB`、`FLUSHALL`，不清空 Asynq archived/retry/scheduled。
2. 关闭旧 app Deployment，确认旧 Pod 全部退出后再启动新版本。旧 Pod 被终止时：
   文档下游计划仍在 `knowledges.processing_fanout`，Wiki 项仍在
   `task_pending_ops`。
3. 只启动一个 `AUTO_MIGRATE=true` 的维护 app，执行 native/custom migration。
   本次 native migration 必须到达 `000089`，并成功创建
   `idx_task_pending_ops_wiki_retry_rotation`。
4. 停止维护 app，再部署正常多副本；正常副本保持 `AUTO_MIGRATE=false`。
5. 使用 `helm/values-production-ha.yaml` 中上述六个参数，不只更新 Wiki 的 900 秒
   超时。
6. 不手工删除旧版 `MaxRetry=3` 的图片任务。旧任务归档后，稳定任务冲突恢复器会在
   PostgreSQL 没有完成凭据时删除仅有的终态 Redis 记录，并用同一 generation/
   stable task ID 按新的 10 次预算重新投递。

迁移后先验证索引和 Pod 参数，再开放上传：

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = current_schema()
  AND indexname = 'idx_task_pending_ops_wiki_retry_rotation';
```

```bash
kubectl -n weknora get pods \
  -l app.kubernetes.io/name=weknora,app.kubernetes.io/instance=weknora,app.kubernetes.io/component=app \
  -o name |
while read -r pod; do
  kubectl -n weknora exec "${pod#pod/}" -- sh -lc '
    printf "%s %s %s %s %s %s\n" \
      "$CUSTOM_WORK_RETRY_IMAGE_MAX_ATTEMPTS" \
      "$CUSTOM_WORK_RETRY_WIKI_MAX_ATTEMPTS" \
      "$CUSTOM_WORK_RETRY_WIKI_INLINE_ATTEMPTS" \
      "$CUSTOM_WORK_RETRY_WIKI_CALL_TIMEOUT_SECONDS" \
      "$WEKNORA_LLM_CHAT_TIMEOUT_SECONDS" \
      "$WEKNORA_MULTIMODAL_TASK_CONCURRENCY"
  '
done
```

若现网 label 不同，用 `kubectl get pod --show-labels` 取得实际 app selector；不要
因为示例 selector 无结果而跳过核验。

## 更新后无丢失核验

先等待 Wiki recovery 与 core fanout recovery 至少完成两个扫描周期。日志应能看到
`wiki queue recovery`、`core fanout recovery`，且不能持续出现同一 stable task
无法恢复的错误。

重复执行更新前 SQL，并额外检查：

```sql
SELECT id, tenant_id, scope_id, dedup_key, fail_count,
       enqueued_at, claimed_at
FROM task_pending_ops
WHERE task_type = 'wiki:ingest'
  AND scope = 'knowledge_base'
ORDER BY scope_id, fail_count,
         CASE WHEN claimed_at IS NULL THEN 0 ELSE 1 END,
         claimed_at, id
LIMIT 200;

SELECT tenant_id, knowledge_id, processing_generation,
       item_id, status, detail, completed_at
FROM custom_enrichment_outcomes
WHERE item_id LIKE 'multimodal.image[%]'
ORDER BY completed_at DESC
LIMIT 200;

SELECT task_type, scope_id, related_id, fail_count,
       last_error, failed_at
FROM task_dead_letters
WHERE task_type IN ('wiki:ingest', 'image:multimodal')
ORDER BY failed_at DESC
LIMIT 200;
```

验收标准：

- Wiki pending 的最老几行不再每批固定为同一组；`claimed_at` 会轮转，正常行能越过
  毒任务完成。
- 真实提供商失败才增加 `fail_count`；断路器拒绝只更新时间并等待。
- 图片任务的独立 worker 运行时，通用后台队列仍持续完成其他任务。
- 有能力完成的图片/Wiki 最终成功；达到 10 次仍失败的项目必须同时有明确业务失败
  状态或 `task_dead_letters` 记录，不能仍显示无限“处理中”。
- 更新前每个在途文档和 Wiki op 都能对账为仍 pending、成功终态或可审计死信。

死信不是成功解析，但也不是丢失。修复输入或模型后，应通过受控重建/重放创建新
generation；不要直接把失败行改成 completed，也不要删除死信后不重新入队。
