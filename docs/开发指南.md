# WeKnora 开发指南

> 当前开发环境核对日期：2026-08-12。开始二次开发前先阅读
> [当前实现架构与文档索引](./custom/当前实现架构与文档索引.md)和
> [二开目录结构规范](./custom/二开目录结构规范.md)。本项目本地后端固定使用
> `custom/tests/runtime_profile_e2e/docker-compose.yml` 的分角色编排，不使用单体
> `app-dev`、`make dev-app` 或 `scripts/dev.sh app`。

## 1. 环境和基础设施

需要 Docker Desktop/Docker Compose、Go、Node.js 和 npm。首次使用时创建环境文件：

```bash
cp .env.example .env
```

先启动基础设施。至少需要 PostgreSQL、Redis、MinIO、Neo4j 和基础 DocReader；
`make dev-start` 仍只负责 `docker-compose.dev.yml` 的基础设施，不启动业务 API：

```bash
make dev-start DEV_ARGS="--minio --neo4j"
```

如果 `.env` 选择了 Qdrant、Milvus 或其他可选依赖，再按实际配置启用对应 Compose
profile。确认基础设施正常后再启动后端角色。

## 2. 分角色后端

runtime profile 使用同一个 Go 镜像，按角色拆分为：

| 角色 | 数量 |
|---|---:|
| API | 3 |
| 解析 worker | 2 |
| 衍生 worker | 2 |
| Wiki worker | 2 |
| maintenance | 2 |
| migration | 1（一次性） |
| runtime DocReader | 2，另有 1 个 DocReader 入口 |
| API 入口 | 1 个 `runtime-entry` |

API 入口对外为 `http://localhost:8080`。首次启动或修改后端代码后执行：

```bash
docker compose -p weknora-runtime-profile-e2e \
  -f custom/tests/runtime_profile_e2e/docker-compose.yml build runtime-api-1

docker compose -p weknora-runtime-profile-e2e \
  -f custom/tests/runtime_profile_e2e/docker-compose.yml up -d --force-recreate

curl http://localhost:8080/health
```

后端代码修改后的完整顺序必须是先停止旧编排，再构建共享镜像，再拉起全部角色：

```bash
docker compose -p weknora-runtime-profile-e2e \
  -f custom/tests/runtime_profile_e2e/docker-compose.yml down

docker compose -p weknora-runtime-profile-e2e \
  -f custom/tests/runtime_profile_e2e/docker-compose.yml build runtime-api-1

docker compose -p weknora-runtime-profile-e2e \
  -f custom/tests/runtime_profile_e2e/docker-compose.yml up -d --force-recreate
```

查看状态和日志：

```bash
docker compose -p weknora-runtime-profile-e2e \
  -f custom/tests/runtime_profile_e2e/docker-compose.yml ps

docker compose -p weknora-runtime-profile-e2e \
  -f custom/tests/runtime_profile_e2e/docker-compose.yml logs -f runtime-entry runtime-api-1
```

## 3. 前端开发

桌面前端开发服务固定使用 `5177`：

```bash
cd frontend
npm ci
npm run dev -- --host 0.0.0.0 --port 5177
```

访问 `http://localhost:5177`。同一开发入口还提供移动端路径
`http://localhost:5177/mobile/`；本项目本地移动端不使用 `5178` 端口。前端代理
默认把 `/api` 和 `/files` 请求转发到 `http://localhost:8080`。

仅修改前端时不需要重启后端 runtime profile；若旧前端进程仍占用 `5177`，先关闭
旧进程再启动新实例。

## 4. 二开目录和验证

大段后端逻辑放在 `internal/custom/`，前端逻辑放在 `frontend/src/custom/`，独立
旁路服务放在 `custom/services/`。新增模块、路由或页面前先按二开目录规范寻找
现有注册点，避免在原生目录复制一套平行实现。

后端角色或二开模块变更后，至少检查：

```bash
go test ./internal/custom/...
```

前端变更后执行：

```bash
cd frontend
npm run type-check
npm run test
npm run build
npm run build:mobile
```

文档队列、Agent 多副本、文件夹、迁移和故障验收入口见
[二开测试索引](../custom/tests/README.md)及各测试目录 README。生产部署不使用本地
开发编排，按[当前版本生产更新部署执行手册](./custom/当前版本生产更新部署执行手册.md)
执行。

## 5. 常见排查

- API 无法访问：先检查 `runtime-entry`、三个 `runtime-api-*` 的 health 状态，再检查
  PostgreSQL、Redis、MinIO、Neo4j 和基础 DocReader。
- 前端请求失败：确认浏览器访问的是 `5177`，并检查 `/api` 代理目标是否为
  `http://localhost:8080`。
- 后端代码修改没有生效：确认已按“down → build runtime-api-1 → up -d --force-recreate”
  顺序重启，而不是只重启单个 API 容器。
- 文档解析失败：同时查看 `runtime-parse-*`、`runtime-docreader-entry` 和基础设施
  日志；不要把 `none` 或排队等待当成失败。
